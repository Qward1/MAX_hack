## 1. Что строим

**ДомСигнал — multi-tenant платформа для подключения домовых MAX-чатов, подготовки обращений и прозрачной обработки проблем подключёнными организациями.**

Одна УК — одно изолированное пространство, далее `tenant`. Один общий MAX-бот и одна Mini App обслуживают все подключённые дома. Для Superadmin и сотрудников организаций есть отдельный обычный веб-кабинет, не Mini App.

Сохраняется прежний путь: сообщение → инцидент → проверенный маршрут → редактируемый черновик → самостоятельная подача во внешний официальный канал → отметка пользователя → наблюдение результата. Добавляется явно согласованный операционный контур: подключение УК/домов, назначения, рабочая очередь и обработка заявок в ДомСигнале.

**Это расширение продукта, а не уже существующая интеграция с ГИС ЖКХ.** Внутренняя заявка УК, сообщение в чате и официальное внешнее обращение не становятся одним объектом. Полноценная CRM с биллингом и всеми процессами ремонтных бригад не входит в эту архитектурную фиксацию.

## 2. Обязательные инварианты — краткая памятка агенту

1. Один общий продукт; не создаём отдельные бот, приложение, БД или сервер на каждый дом/УК.
2. Управление домом, полномочия человека в УК и права человека в MAX-чате — три независимые проверки.
3. `bot_added` начинает обнаружение установки, но не выдаёт роль и не подтверждает дом.
4. Ссылка, код, `start_param`, название чата и выбор адреса сами по себе не дают доступ.
5. Backend проверяет tenant, дом, объект и действие. `allowed_actions` описывает результат проверки, а не заменяет её.
6. Один дом может иметь несколько чатов; один активный групповой чат в MVP относится к одному дому. Сотрудник может отвечать за несколько домов.
7. Сообщение жителя, общий инцидент, рабочая заявка УК и внешнее обращение разделены; приватные тексты не публикуются соседям автоматически.
8. «Пользователь отметил подачу» не означает внешнюю регистрацию. «Исполнитель сообщил о выполнении» не означает подтверждение жителя.
9. LLM предлагает категорию, поля и кандидатов. Core принимает решения о доступе, связывании, назначении, сроках и записи.
10. Личный сценарий остаётся работоспособным без группового доступа и без LLM; это не обход tenant/house-проверок.
11. История сохраняется при смене сотрудника, чата или УК. Нельзя переписать `tenant_id` старых заявок и раскрыть их новой УК.
12. `TARGET`, `IMPLEMENTED IN BRANCH`, `MERGED TO MAIN`, `LIVE VERIFIED` — разные состояния. Ни документ, ни mock-тест не повышают зрелость функции автоматически.

## 3. Контуры приложения

```text
Жители                        Сотрудники УК / Superadmin
  │                                     │
MAX-группа / личный бот / Mini App       Обычный веб-кабинет
  └───────────────────┬─────────────────┘
                 HTTPS / API / webhook
                        │
       Авторизация и tenant/house/object scope
                        │
       Application services → domain/core
          │            │             │
      AI-модуль     PostgreSQL    Integration adapters
                       │             │
                 durable worker ─── MAX Bot API
```

Сохраняем текущий модульный монолит: один backend-пакет/образ, процесс API с webhook и отдельный worker, PostgreSQL, существующий HTTPS edge. Web-кабинет — отдельная пользовательская поверхность с общей backend-логикой; отдельный backend-сервис ему не требуется.

Mini App использует принятый React/MAX UI и изолированный MAX Bridge wrapper. Веб-кабинет открывается в обычном браузере без обязательного Bridge. Точные пути frontend entry points определяются по реальному foundation в соответствующей задаче — сейчас второй scaffold не создаём.

Логические модули: identity/access; organizations/onboarding; houses/management; chat connections; intake/incidents; tickets/routing; appeals; notifications; audit; AI. Это не перечень микросервисов и не требование создать пустые каталоги заранее.

Без нового обоснования не добавляем Redis, RabbitMQ/Kafka, отдельный identity service, Kubernetes, vector DB или новый framework. Количество процессов и экземпляров увеличивается после замеров, не по числу домов в презентации.

## 4. Сущности и связи

Названия ниже описывают смысл; это не окончательная SQL-схема или список обязательных новых таблиц. Сначала сопоставить их с существующими сущностями.

| Сущность | Смысл и важная граница |
|---|---|
| `ManagementCompany / Tenant` | Организация, режим доступа, лимиты подключений. Не владеет токеном общего бота |
| `OnboardingApplication` | Заявка УК, представитель, рассмотрение, решение и основания |
| `House` | Физический дом со стабильной идентичностью и происхождением адреса |
| `HouseManagement` | Какая УК управляет домом, на каком основании и в какой период |
| `User + Identity` | Пользователь и подтверждённые способы идентификации; MAX ID не равен роли |
| `OrganizationMembership` | Роль пользователя в конкретной организации |
| `HouseAssignment` | Назначение сотрудника на конкретную HouseManagement; при смене УК не переносится автоматически |
| `ResidentMembership` | Основание доступа к дому, уровень проверки, срок и отзыв; не реестр собственников |
| `MAXChat` | Стабильный внешний идентификатор, тип и технические сведения о чате |
| `BotInstallation / ChatBinding` | Бот в чате, дом и период управления, охват, права, проверки и состояние |
| `ConnectionRequest` | Ограниченное по времени разрешение на конкретное подключение и его подтверждения |
| `Report` | Индивидуальное сообщение жителя; собственный автор и история |
| `Incident` | Общая проблема конкретного дома/места, связывающая сообщения |
| `Ticket` | Внутренняя рабочая заявка, очередь, текущий владелец и обработка |
| `AppealDraft / ExternalAppeal` | Редактируемый текст; сведения о внешнем обращении и источнике подтверждения |
| `RoutingRule / Queue` | Правило назначения и очередь сотрудников |
| `WorkAttempt / ResultObservation` | Попытка с конкретным отчётом о выполнении и отдельные наблюдения именно этой попытки |
| `AuditEvent / Notification` | Кто изменил состояние; что и кому предполагалось доставить, результат доставки |

Основные связи: Tenant → HouseManagement → House; User → OrganizationMembership/HouseAssignment; House → несколько ChatBinding; User → несколько ResidentMembership; Report → Incident → Ticket; ExternalAppeal связывается с инцидентом, но не подменяется Ticket.

Для основного управляющего контура MVP конфликтующие активные притязания разных УК на один дом не активируются автоматически: требуется проверка. Общий чат сразу нескольких домов исключён из автоматической маршрутизации MVP; нужен явный выбор дома либо последующее отдельное решение.

Счётчик сообщений и число уникальных участников — разные показатели. Ни один из них не называется числом всех реально пострадавших жителей.

## 5. Доступ и RBAC

| Роль | Область | Разрешённые действия |
|---|---|---|
| Superadmin | Платформа | Одобрять УК, задавать лимиты, разбирать споры, приостанавливать подключения, смотреть эксплуатационный аудит |
| Администратор УК | Собственный tenant | Добавлять дома на проверку, приглашать сотрудников, назначать ответственных, управлять подключениями, очередями и аналитикой |
| Ответственный за дом | Назначенные дома | Подключать чаты при делегировании, координировать заявки и исполнителей, контролировать результат |
| Сотрудник/оператор | Разрешённые дома, очереди и задачи | Принимать, уточнять, выполнять и комментировать заявки; менять разрешённые рабочие состояния |
| Житель | Собственные обращения и разрешённая общая доска | Сообщать о проблеме, присоединяться к инциденту, видеть свой результат, подтверждать или оспаривать устранение |

Уточнение A-15 от 18.09.2026: «ответственный» — role `responsible` в HouseAssignment на HouseManagement, не organization-level role. Organization roles — `company_admin` и `operator`; operator требует assignment, company_admin видит текущие management своей УК. House не хранит permanent tenant_id; Incident сохраняет исходные house_id + management_id. Периоды управления полуоткрытые `[from, to)`, одновременные active пересечения запрещены. Не нужен произвольный конструктор ролей. Администратор MAX-чата получает только ограниченную возможность подтвердить подключение, если не имеет отдельной роли в организации.

Для каждого обращения к данным проверяется: `identity → organization membership / resident basis → house scope → object scope → action`. Тот же подход применяется в bot handlers, HTTP API, worker, экспортах и доступе к вложениям. Tenant из браузера или текста сообщения не считается доверенным.

Superadmin по умолчанию видит эксплуатационные сведения, а не всю личную переписку. Доступ поддержки к содержимому — отдельное контролируемое действие с аудитом.

**Идентификация:** в Mini App проверяем подписанные стартовые данные MAX на backend [M7–M8]. Для отдельного веб-кабинета — учётные записи по приглашению, отзыв сессий и MFA для привилегированных ролей. Конкретный механизм web-auth выбрать в своей задаче; не придумывать универсальный MAX OAuth и не делать бота сервисом доставки OTP для внешней системы [M12].

## 6. Подключение организации и дома

| Этап | Действие | Условие выхода |
|---|---|---|
| Заявка | Представитель указывает УК, контакты, дома и объём | Создана заявка без доступа к данным домов |
| Проверка УК | Superadmin проверяет организацию и представителя | Tenant одобрен, первый администратор назначен |
| Лимит | Задаётся число активных домов, например 20 | Лимит действует на активацию; это наше правило, не лимит MAX |
| Дома | Выбор/импорт адресов и основания управления | Подтверждённая HouseManagement, спорные записи не активны |
| Назначения | Ответственный, сотрудники и резервная очередь | Известен владелец следующего действия |
| Чат | Создание ConnectionRequest и верификация по разделу 7 | Активная проверенная привязка |
| Запуск | Проверка прав, режима, доступов, уведомлений | Дом готов к приёму и маршрутизации |

В MVP проверка УК и управления домом ручная, с источником, датой и проверившим. Это не имитация API ГИС ЖКХ.

Лимит считаем по активным домам, не по числу их чатов. Незавершённое подключение может иметь истекающий резерв. Повторная доставка события и параллельная активация не должны дважды списать лимит или обойти его. Точные TTL и правила резерва уточняются в задаче подключения.

## 7. Верификация MAX-чата

**Согласованный механизм — две стороны подтверждения:** организация разрешает привязку к дому; действующий администратор MAX-чата доказывает технические полномочия. Совпадение этих ролей у одного человека не превращает добавление бота в автоматическую верификацию адреса. Для первого/спорного подключения или смены УК предусмотрена дополнительная проверка платформой.

1. **Разрешение УК.** В кабинете создаётся ConnectionRequest на конкретный tenant/дом, инициатора и допустимого подключающего. Можно пригласить действующего администратора чата без выдачи ему доступа к рабочим заявкам УК.
2. **Установка.** Человек добавляет общего бота и выдаёт необходимые права. `bot_added` даёт `chat_id`, добавившего пользователя, время и `is_channel` [M1–M2]. Создаётся только ожидающая установка.
3. **Действие внутри чата.** Администратор запускает наш `/connect` или настройку карточки. Это наша команда, не специальный endpoint MAX. Backend связывает реального отправителя и чат из события. Секрет не публикуется в общем чате.
4. **Проверка MAX.** Backend проверяет членство/права бота и текущие административные права человека, а не только исторический `bot_added` [M3–M5]. Не удалось проверить — остаётся pending, а не success.
5. **Мастер в Mini App.** Подписанная идентичность должна соответствовать подключающему. Мастер показывает выбранные дом, УК, чат и охват. Временный server-side контекст связывает шаги; URL самостоятельно не выдаёт полномочий [M7–M9].
6. **Подтверждение УК.** Уполномоченный сотрудник проверяет соответствие чата дому. Название/аватар — подсказки, не доказательства. Сохраняются основания и два результата проверки.
7. **Активация.** Повторно проверяются tenant, период управления, назначение, права, отсутствие конфликта привязки и лимит. Создаются активная связь и audit event, разрешение закрывается.

Показать отдельно: **«Права в MAX проверены»** и **«Соответствие дому подтверждено организацией»**. Не писать «MAX подтвердил адрес дома».

Состояния подключения по смыслу: ожидает установки → ожидает проверки → активно → приостановлено / удалено / архивировано. Причина приостановки и дата последней проверки видны. Это пока не требование немедленно заменить существующий enum.

Для группового анализа нужен проверенный набор прав; документирован `read_all_messages` [M6]. Не запрашиваем управление участниками, администраторами и ссылкой чата без необходимости. Закрепление — опциональная возможность. Если `is_channel=true`, групповой мастер не принимает канал как домовой чат.

До активации не анализируем и не сохраняем всю переписку: используем только минимальные события установки/подтверждения. При повторном событии не создаём вторую установку. При подмене дома/пользователя, истёкшем разрешении или отзыве полномочий подключение отклоняется.

**Граница доказательства:** механизм защищает от случайной/чужой привязки, но сам по себе не доказывает соответствие физическому дому при сговоре уполномоченных лиц. Нужны основания, аудит и оспаривание, а не обещание абсолютной проверки MAX.

## 8. Mini App и доступ жителей

Одна HTTPS Mini App привязана к общему боту [M1, M9]. Не создаём приложение на дом.

```text
Валидация MAX initData
  → идентификация пользователя
  → доступные tenant/house scopes
  → разрешение контекста запуска
  → экран и allowed_actions
```

| Вход | Поведение |
|---|---|
| Из привязанного чата | Подписанный chat-контекст — подсказка; backend проверяет binding и доступ |
| По ссылке на инцидент | Проверяем объект в scope пользователя; чужая ссылка не открывает данные |
| Из личного диалога | Последний доступный дом либо выбор; исходный групповой chat_id не предполагается |
| Без house-контекста | Выбор из разрешённых домов или запрос доступа |
| Несколько домов | Явный переключатель и видимый адрес перед отправкой |
| Недопустимый дом/контекст | Понятный отказ или запрос подтверждения; не отправляем молча в другой дом |

`initData` документирует пользователя, `chat` и `start_param`, но нельзя предполагать одинаковый исходный чат для всех способов запуска [M7]. `initDataUnsafe` не является доказательством авторизации [M7–M8]. Техническую работу каждого пути проверяем в реальных MAX Web/mobile.

Основания доступа жителя:
- Указал адрес: может создать собственное сообщение в разрешённом канале с пометкой непроверенной связи; чужая доска недоступна.
- Проверено участие в подключённом чате: разрешённая обезличенная доска в охвате привязки.
- Связь с домом подтверждена организацией: доступ по согласованной политике дома.

Ни одно основание автоматически не подтверждает право собственности. Проверяем конкретного пользователя, не импортируем всех участников в «реестр жителей» [M5]. При выходе/отзыве основание пересматривается; независимые действующие основания учитываются отдельно. Собственные обращения не теряются при потере доступа к общей доске.

Сохраняем пять пользовательских экранов B-00: доска дома, новая проблема, инцидент, черновик, моя история. Выбор дома, источники и мастер подключения — контекстные поверхности. Веб-кабинет сотрудников не ограничивается этими пятью экранами.

## 9. Сообщение, рабочая заявка и результат

### Маршрутизация

Дом определяется активной привязкой чата или подтверждённым выбранным контекстом. NLP предлагает категорию/место и уточнения. Backend использует дом, категорию, объект, действующие настройки обслуживания и назначения для выбора очереди.

Несколько подходящих сотрудников → общая очередь; один принимает текущую ответственность. Соисполнители допустимы, но следующий шаг всегда имеет владельца. Нет назначения/сотрудник недоступен/категория неизвестна → резервная диспетчерская очередь tenant.

Общедомовой инцидент объединяет сообщения, а не удаляет их. Связывание не лишает жителя возможности подать собственное обращение. По нескольким чатам одного дома публикуются только разрешённые общие сведения; приватный текст одного чата не копируется в другой.

### Два разных направления после инцидента

| Направление | Честный результат |
|---|---|
| Рабочий контур подключённой УК | Заявка действительно сохранена и поставлена в очередь ДомСигнала; это внутренняя регистрация |
| Внешний официальный канал | Подготовка текста, переход и отдельная отметка пользователя; подтверждение регистрации только из реального внешнего источника |

Обнаружение проблемы в группе не является согласием отправить от имени человека персональное официальное обращение. Неактивный tenant или ненастроенная очередь не показываются как успешно принявший исполнитель.

### Рабочий lifecycle

Целевая последовательность, не окончательная state machine: новая → принята →
в работе → выполнение заявлено → проверка результата → закрыта. Условия
закрытия/возобновления окончательно согласуем в следующей итерации A-16.

Дополнительные состояния по смыслу: нужно уточнение; ожидается внешняя сторона; отменена с причиной. Просрочка — признак конкретного применимого срока, не универсальный рабочий статус.

Отчёт исполнителя и наблюдение жителя связаны с конкретной попыткой выполнения. «Исправлено» и «Проблема осталась» от разных участников сохраняются как расхождение и требуют проверки; большинство голосов его не скрывает. Нет ответа жителя → нет подтверждения жителем.

Ticket имеет стабильный внутренний номер/ID, время создания, источник,
management/house context и историю решений/работ. Это не номер ГИС ЖКХ.
WorkAttempt хранит конкретный отчёт, ResultObservation ссылается на конкретную
попытку. Позднее возражение к последней попытке нельзя потерять из-за уже
записанного подтверждения другого жителя. Выполнение, проверка и закрытие
раздельны; здесь не выбирается автоматическое правило reopening.
Одна работа может объединить сигналы без удаления исходных Report, связей
с заявителями и их индивидуальной истории. Ответственный/резервная очередь
и следующий шаг определяются для поддерживаемого внутреннего процесса;
неизвестная ответственность требует диспетчерской проверки, не любая категория
автоматически входит в обязательства УК.

Существующие `Incident.status`, `reported/overdue/escalated` и DTO B-00 нельзя молча заменить статусами Ticket. В контрактном срезе нужно явно описать отображение и совместимость. Подготовка эскалации не равна отправке жалобы.

Уведомления — только разрешённым адресатам, с учётом остановки бота, доступности канала и условий платформы [M12]. Ошибка доставки не отменяет сохранённую заявку и не считается успехом уведомления. Опасная ситуация выводится из обычного ожидания по ранее согласованному safety-пути.

### Сквозной MAX-путь — PLANNED

**Report → Incident → Ticket → WorkAttempt → outbox → сообщение MAX →
открытие соответствующей карточки Mini App → проверка пользователем →
ResultObservation → обновление состояния и карточки.**

Для группы исходный поддержанный вход A-07 — явная `/report`, не автоматический
анализ переписки. Весь новый путь PLANNED / NOT RUN; live остаётся PENDING TOKEN.

Ссылка задаёт контекст, не права, и её открытие не меняет бизнес-состояние.
Карточка читает свежие данные API; callback повторно проверяет actor, scope и
актуальную попытку. Перед отправкой заново проверяются получатели, отзыв доступа,
смена management/binding. Sharing cancel не отправка, mobile-only имеет fallback.
API accepted не означает прочтение: намерение создано / ожидает / API принял
отправку / ошибка или неизвестный результат — состояния доставки, не Ticket.
Ошибка MAX не откатывает сохранённую работу, exactly-once внешней доставки
без доказанного механизма не обещается. [Методы и ограничения](MAX_LIVE_SMOKE.md#методы-max--документальная-сверка-18092026).

## 11. UI отдельного веб-кабинета

| Пользователь | Разделы |
|---|---|
| Superadmin | Заявки УК; организации/лимиты; спорные привязки; состояние системы и аудит |
| Администратор УК | Обзор; дома/чаты; сотрудники/назначения; обращения/очереди; маршрутизация; аналитика |
| Ответственный/оператор | Мои дома; моя очередь; карточка заявки; комментарии; отчёт/проверка результата |

Ключевой экран «Готовность дома»: управление подтверждено → ответственный назначен → чат проверен → права достаточны → очередь настроена → приём включён. Каждый незавершённый этап имеет причину и следующее действие.

Mini App и кабинет используют одну бизнес-логику и реальные API, но разные auth entry points и навигацию. У каждой поверхности loading/empty/error/unauthorized/forbidden/stale; темы, клавиатура и длинные данные не ломают layout. Backend возвращает разрешённые действия, интерфейс не угадывает их из статуса.

## 12. Контракты, совместимость и масштабирование

### Контрактные требования, не готовые endpoints

Согласовать в существующем `docs/CONTRACTS.md`: tenant/house context; role assignments; основание resident-access; состояние и причина подключения; лимит/резерв; допустимые действия; очередь/назначение; различие Report/Incident/Ticket/ExternalAppeal; тип происхождения и актуальность; ошибки доступа/конфликта/проверки.

Не менять одновременно весь API. Сначала минимальный совместимый read-model и consumer/producer tests, затем новые действия. TS types генерируются из принятого источника схем. Новая роль не даёт доступ к старым объектам без scope. Неподдержанная функция не появляется активным CTA.

Сохраняем `allowed_actions`, capabilities и provenance B-00. Backend capabilities — готовность функции; Bridge capabilities — доступность клиентского метода. Это разные вещи. Demo-маркер никогда не исчезает из-за официального источника, на котором основан тестовый пример.

### Масштабирование

Core: identity/access, lifecycle подключения, инциденты/заявки, действия, аудит, доставка, UX-паттерны. Variable: региональные правила, организации, дома, исполнители, языки и интеграционные адаптеры.

| Масштаб | Следующий ресурс/изменение, не обещание измеренной ёмкости |
|---|---|
| 1 УК / 3 дома | Ручная проверка, одна платформа, базовый аудит и очереди |
| 10 УК / 500 домов | Импорт, пакетные назначения, индексы/пагинация, изоляция и метрики tenant |
| Сотни УК / тысячи домов | Измерение пиков, дополнительные API/worker, справедливые очереди и операционные регламенты |

MAX указывает общий предел запросов; конкретные действующие значения и ограничения методов нужно учитывать перед реализацией [M11]. Больше worker не повышает лимит платформы. Схлопываем обновления карточки, ограничиваем отправку, не делаем webhook на каждый дом. Предел чатов для одного бота не считаем неограниченным без подтверждения MAX.

Tenant scope проходит через запросы, выборки, файлы, кеши, jobs, аналитику и экспорт. Это выбранное требование нашей архитектуры, не функция MAX.

## 15. Критерии хакатона и границы обещаний
