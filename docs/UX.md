# ДомСигнал — UX contract B-00

## Статус и границы

Версия `v0.1` описывает целевой UX для реализации после foundation. Это не
утверждение о готовности экранов или API. Фактически доступные и целевые
endpoints разделены в [CONTRACTS.md](CONTRACTS.md).

Backend — источник бизнес-состояния, provenance и разрешённых действий. UI не
выводит права из статуса: capability-gated функции скрываются, а действия
инцидента рендерятся из `allowed_actions`. Deep link задаёт начальный экран, но
никогда не предоставляет доступ. Региональные адресаты, каналы, основания и
сроки приходят с backend и не зашиваются во frontend.

## Личный golden path

Этот путь не зависит от доступа бота к групповому чату:

1. Пользователь запускает личный сценарий, выбирает доступный дом и описывает
   проблему текстом. Фото и голос показываются только при соответствующих
   capabilities и не нужны для завершения пути.
2. Backend анализирует описание. Экстренный сигнал немедленно включает
   Emergency Mode; обычный путь не ждёт LLM. При низкой уверенности или сбое
   анализа пользователь выбирает категорию вручную.
3. Пользователь видит распознанные `ProblemDetails`, исправляет описание,
   категорию и место, затем подтверждает. Backend создаёт новый инцидент или
   возвращает существующий; решение о совпадении не принимает frontend.
4. В карточке инцидента показаны маршрут, основание, provenance и доступные
   действия. Пользователь выбирает «Подготовить обращение».
5. Редактируемый черновик создаётся и хранится на backend. Изменения переживают
   reload после подтверждённого сохранения; состояние «Сохранено» показывается
   только после успешного `PATCH`.
6. Пользователь копирует текст и/или открывает официальный внешний канал,
   самостоятельно отправляет обращение и возвращается. Копирование и переход
   во внешний канал не считаются отправкой.
7. Только явное действие «Я отправил(а) обращение» записывает пользовательскую
   отметку. Подтверждение UI неизменно по смыслу:

   > Вы отметили обращение как отправленное.<br>
   > Регистрация во внешней системе ДомСигналом не подтверждена.

8. В Incident Detail и My Activity появляются статус, напоминание или следующий
   разрешённый шаг. `reported` означает только эту отметку пользователя, а не
   подтверждённую регистрацию внешней системой.

## Общие состояния и правила

| Состояние | UX-правило |
|---|---|
| Loading | Сохранять каркас и контекст дома; блокировать только зависимое действие, не весь интерфейс. Повторное нажатие не создаёт второй запрос. |
| Empty | Объяснить, чего пока нет, и дать одно доступное следующее действие. Пустой список не показывается как ошибка. |
| Error | Показать понятный `title/detail`, `trace_id` для поддержки и «Повторить» только при `retryable=true`; введённый текст не очищать. |
| Unauthorized (`401`) | Сообщить, что сессия MAX недействительна или истекла, предложить безопасно открыть mini app заново; не раскрывать детали проверки `initData`. |
| Forbidden (`403`) | Сообщить, что дом или действие недоступны этому пользователю; не предлагать получить доступ через deep link. |
| Stale (`409` или версия изменилась) | Не затирать локальный ввод. Получить актуальную версию, показать, что изменилось, и предложить повторить разрешённое действие. |
| Offline/network | Сохранить несданный ввод в текущей сессии, показать состояние соединения и безопасный retry; не показывать успешный результат до ответа backend. |

Кнопка из `allowed_actions` показывается только для известного `code`. При
`enabled=false` она disabled и рядом доступен `reason`; отсутствующее действие
не синтезируется. Неизвестные статус/action/provenance безопасно отображаются
как «Состояние обновилось» с reload, но не превращаются в разрешённое действие.

## 1. Home / House Board

**Purpose.** Быстро выбрать доступный дом, увидеть его актуальные инциденты и
начать личное сообщение о проблеме.

**Входные данные.** `UserContext`, список `HouseSummary`, выбранный `house_id`,
список `IncidentSummary`; опционально безопасный deep-link context.

**Основные блоки.** Заголовок/переключатель дома; заметная provenance-плашка
дома; сводка по статусам; карточки инцидентов с категорией, местом, статусом,
временем обновления, числом сообщений/участников и следующим разрешённым
действием; входы «Сообщить о проблеме» и «Моя активность».

**Действия и переходы.** Выбор дома обновляет доску; карточка открывает Incident
Detail; «Сообщить о проблеме» — Report Problem; `join` выполняется только при
полученном action descriptor; «Моя активность» — My Activity. Deep link после
server-side проверки может открыть нужный инцидент, иначе остаётся на доске с
сообщением об отказе.

**Состояния.** Loading — skeleton карточек и заблокированный выбор дома. Empty —
«В этом доме пока нет активных проблем» и CTA личного отчёта. Error — inline
retry без очистки выбранного дома. Unauthorized — экран повторного входа.
Forbidden — недоступный дом не попадает в переключатель; прямой запрос даёт
явный отказ. Stale — баннер «Данные обновились» и фоновый reload; карточки не
переставляются во время нажатия.

**Mobile / web MAX.** На mobile — один столбец, sticky CTA и bottom-sheet выбора
дома; на web — ограниченная ширина, список и detail могут быть рядом. Порядок,
данные и конечные действия одинаковы; hover, haptics и MAX Bridge не являются
обязательными.

## 2. Report Problem

**Purpose.** Принять свободное описание, безопасно проанализировать его, дать
исправить результат и передать подтверждённые данные backend.

**Входные данные.** Доступный `house_id`, необязательный начальный текст,
capabilities, затем `ProblemAnalysis` и редактируемые `ProblemDetails`.

**Основные блоки.** Поле описания; capability-gated фото/голос; прогресс
анализа; карточка распознавания с категорией, местом и недостающими полями;
ручной выбор категории; кандидаты существующих инцидентов; Emergency Mode при
сигнале риска.

**Действия и переходы.** «Проанализировать» вызывает target analyze; пользователь
редактирует распознанное и подтверждает target report. Backend возвращает новый
или существующий инцидент, после чего открывается Incident Detail. Выбор
существующего кандидата не даёт доступ сам по себе: join доступен только по
`allowed_actions` и проверяется backend.

**Состояния.** Loading — введённый текст остаётся видимым, доступна отмена
ожидания без потери ввода. Empty — пустое/слишком короткое описание получает
локальную подсказку, запрос не отправляется. Error — retry или «Выбрать вручную»;
сбой LLM/NLP никогда не блокирует отправку. Unauthorized/forbidden — ввод
сохраняется в текущей сессии, отправка заблокирована до восстановления сессии
или выбора разрешённого дома. Stale — при изменении кандидата backend заново
решает create/join; UI не обещает прежний результат matching. Validation errors
привязываются к полям из `field_errors`.

**Mobile / web MAX.** На mobile — полноэкранная форма и нативно доступная
клавиатура; на web — компактная форма с review рядом. В обоих клиентах текстовый
ввод и ручная категория дают одинаковый результат без media/Bridge.

## 3. Incident Detail

**Purpose.** Показать одно авторитетное состояние проблемы, объяснимый маршрут,
историю пользовательских отметок и только разрешённые следующие шаги.

**Входные данные.** `IncidentDetail`, его `allowed_actions`, route/provenance и
текущий `UserContext`.

**Основные блоки.** Заголовок и один из семи статусов; описание/место;
provenance; маршрут с адресатом, основанием и датой проверки; счётчики;
краткая timeline; блок следующего шага. Для `reported` рядом всегда пояснение,
что внешняя регистрация не подтверждена ДомСигналом.

**Действия и переходы.** `prepare_appeal` открывает Appeal Draft; `join`,
`mark_resolved`, `mark_unresolved`, `escalate` и `report_not_problem`
отправляются только при соответствующем descriptor; `retry` повторяет
безопасную операцию. Source link открывает Provenance Drawer, а не новый
основной экран.

**Состояния.** Loading — skeleton с сохранённым back target. Empty — если
инцидент удалён/недоступен, возврат на доску без подмены на «решён». Error —
retry по error contract. Unauthorized — повторный вход. Forbidden — отказ без
раскрытия частных данных дома. Stale — актуальная карточка загружается перед
мутацией; disabled action показывает server reason. При конфликте feedback UI
показывает расхождение наблюдений, не выбирая «истину» голосованием.

**Mobile / web MAX.** На mobile блоки идут одной лентой, главное действие
закреплено снизу; на web источник и timeline могут быть во второй колонке.
Семантика статуса и действий идентична.

## 4. Appeal Draft

**Purpose.** Дать пользователю отредактировать и надёжно сохранить текст,
передать его во внешний официальный канал и отдельно записать self-report.

**Входные данные.** `AppealDraft`, версия/время сохранения, route и официальный
channel descriptor, `allowed_actions`.

**Основные блоки.** Редактируемое поле текста; «Сохраняется… / Сохранено
<time> / Не сохранено»; адресат и provenance; предупреждение «ДомСигнал
подготавливает черновик, но не отправляет его»; кнопки копирования, открытия
канала и ручной отметки.

**Действия и переходы.** `edit_draft` сохраняет новую версию на backend;
`copy_draft` копирует текущий сохранённый/видимый текст; `open_official_channel`
открывает внешнюю ссылку и не меняет статус; после возврата `mark_filed`
записывает только пользовательскую отметку и ведёт в Incident Detail/My
Activity. Текст остаётся editable до тех пор, пока это разрешает backend.

**Состояния.** Loading — поле read-only до загрузки серверной версии. Empty —
пустой сгенерированный текст заменяется редактируемым безопасным шаблоном от
backend, не frontend. Error сохранения — текст остаётся на экране, копирование
доступно, а mark/open предупреждают о несохранённых изменениях. Unauthorized /
forbidden — текст не раскрывается до успешной проверки доступа. Stale — при
version conflict локальный текст не затирается; показываются актуальная и
локальная версии с повторным сохранением. Reload загружает последнюю
подтверждённую backend-версию.

**Mobile / web MAX.** На mobile — крупная textarea, системное копирование и
возврат из внешнего приложения; на web — textarea и действия рядом, переход
может открыть вкладку. Ни событие visibility/focus, ни сам launch URL не
считаются отправкой.

## 5. My Activity

**Purpose.** Вернуть пользователя к своим отчётам, черновикам, отметкам,
напоминаниям и следующему шагу без группового контекста.

**Входные данные.** Страница `ActivityEvent` и связанные `allowed_actions`.

**Основные блоки.** Хронологический список; фильтры «Нужно действие / В работе /
Завершено» как представление, не новые incident statuses; карточка с домом,
инцидентом, событием, provenance, напоминанием и следующим шагом.

**Действия и переходы.** Открыть Incident Detail или сохранённый Appeal Draft;
выполнить разрешённый следующий шаг. UI не создаёт reminder/escalation сам —
он отображает данные backend.

**Состояния.** Loading — skeleton timeline. Empty — «У вас пока нет действий» и
переход на House Board. Error — retry с сохранением фильтра. Unauthorized —
повторный вход; forbidden для отдельной записи — скрыть содержимое и предложить
обновить список. Stale — новые события добавляются после refresh без
дублирования; статус карточки берётся из последнего ответа backend.

**Mobile / web MAX.** На mobile — компактная timeline и фильтры-чипы; на web —
список с панелью деталей. Состав событий и следующий шаг одинаковы.

## Контекстные режимы

### Source / Provenance Drawer

Drawer открывается из дома, маршрута, срока, статуса подачи и других данных,
влияющих на решение. Показывает тип происхождения, источник/ссылку, дату
проверки или фиксации и пояснение. Обязательная семантика:

| Type | Отображение |
|---|---|
| `official` | «Официальный источник · проверено <date>»; рядом название и ссылка на источник. |
| `product_derived` | «Рассчитано ДомСигналом на основе указанных правил»; доступны использованные правила и их provenance. |
| `user_reported` | «Указано пользователем · внешней системой не подтверждено»; доступна дата отметки. |
| `demo` | «Демонстрационные данные»; контрастная постоянная метка, без официального визуального стиля. |

Источник, дата проверки и demo-state видимы прямо в основном блоке, если от них
зависит решение; drawer даёт детали, но не прячет критичную маркировку. Неизвестная
или просроченная проверка показывается честно, без выдуманного срока.

### Emergency Mode

Это приоритетное состояние внутри Report Problem или Incident Detail, а не
шестой экран. Backend возвращает признак и инструкции до/без LLM. UI сразу
показывает предупреждение, безопасные действия и контакты из регионального
пакета с provenance; обычный маршрут, draft и ожидание анализа уходят ниже.
ДомСигнал не обещает диагностику или устранение и не hardcode контакты во
frontend. Сбой дополнительного анализа не скрывает emergency instructions.

### Admin Mode

Это capability- и permission-gated представление House Board/Incident Detail,
а не отдельный основной экран. При `capabilities.admin=false` входы отсутствуют.
Администратор с server-side доступом видит агрегированную сводку дома,
anti-spam/quiet settings и разрешённое dismiss false positive; provenance и
demo-marking сохраняются. Admin capability не заменяет проверку конкретного
дома, а deep link не повышает роль. Ошибка сохранения настроек не меняет
отображаемое подтверждённое значение.

## Статусы и честные пользовательские тексты

UI поддерживает только `detected`, `open`, `reported`, `overdue`, `escalated`,
`resolved`, `dismissed`. Для `reported` допустимы «Вы отметили как
отправленное» и «Житель отметил отправку». Без фактического ответа внешней
системы запрещены формулировки «обращение зарегистрировано», «ГИС ЖКХ приняла
обращение» и «официальная регистрация завершена».
