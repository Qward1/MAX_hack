# ДомСигнал — масштабирование

Коротко: что одинаково для всех, что меняется от города к городу и от УК к
УК, как УК подключается сама, сколько стоит чат, что показал нагрузочный
прогон и где пределы. Состояние на 24.09.2026 (срез D2).

## Ядро и переменная часть

| Ядро — один код для всех | Переменная часть — данные и настройки |
|---|---|
| Доступ: УК → дом → объект → действие; житель по участию в чате или открытому доступу | **Пакет региона** `regions/<код>`: каналы, органы, правила маршрута с источниками. Второй регион RU-MOW — данными, без `if region` ([REGION-MOW](decisions.md#region-mow-2026-09-26)) |
| Приём реплик, окна, правила опасности в транзакции приёма | **Профиль дома**: регион, муниципалитет, территория (`uk` / `municipal` / `mixed`) |
| Сигналы, заявки УК, проверка результата жителями, аудит | **УК**: заявка, одобрение, **квота чатов**, сотрудники и назначения на дома |
| Роутер ответственности, карточка следующего шага, черновик обращения | **Чаты**: подключение A-07 с проверкой прав в MAX, чтение включается у привязки |
| Очередь задач в PostgreSQL, пулы `operational` и `ai`, доставка через outbox | **Провайдер модели**: `LLM_PROVIDER`, профиль модели, дневной бюджет, выключатель `PASSIVE_LLM_ENABLED` |

Новый город — новый каталог `regions/`, профиль его домов и проверка
`scripts/validate_region_pack.py` (валидатор не пропустит канал, недоступный
в регионе пакета). `route_preview --compare-regions` печатает Казань и Москву
рядом — один код, разные каналы и основания.

## Как УК подключается сама

1. Страница продукта `/site` (в обычном браузере — и корень сайта) → «Подключить УК».
2. Заявка: организация, ИНН, контакт, **сколько чатов** подключить, адреса.
   Заявитель получает секретную ссылку на страницу статуса.
3. Платформа проверяет организацию, задаёт вопросы (ответ — на той же
   странице) и одобряет с квотой чатов Q.
4. На странице статуса — «Создать аккаунт администратора»: логин, пароль,
   приложение-аутентификатор. Ссылку никто не передаёт вручную.
5. Администратор входит через `/login`, запрашивает управление домами,
   приглашает сотрудников (или платформа открывает регистрацию по ссылке),
   подключает чаты своих домов. Каждый чат — один слот квоты; кончились
   слоты — «Запросить расширение», решение платформы — полностью, частично
   или отказ с причиной ([CHAT-QUOTA](decisions.md#chat-quota-2026-09-26)).
6. Обзоры УК и платформы считают всё по данным базы без текстов жителей.

Окончательная проверка квоты — в транзакции активации привязки под
блокировкой строки УК: две активации за последний слот дают одну
(PostgreSQL-тест гонки из двух и из четырёх активаций).

## Стоимость

≈ **12 ₽ в месяц на чат**: загруженный реальный чат (Telegram, 25 485
сообщений, D1-агрегаты) даёт в среднем 6,67 окна разбора в сутки; окно стоит
≈ 0,06 ₽ при выбранном профиле модели (P6: `minimal`, flex) → 6,67 × 0,06 ×
30 ≈ 12 ₽. Спокойный чат (WhatsApp, 1,54 окна в сутки) — ≈ 2,8 ₽. Источник —
[отчёт оценки P6](../evaluation/reports/2026-09-23-p6-evaluation.md) §7 и
`evaluation/reports/2026-09-23-p6-d1-aggregates.json` (только числа, без
текстов). Правила опасности, окна и доставка работают и без модели;
выключатель `PASSIVE_LLM_ENABLED=false` снимает эту статью расходов.

## Нагрузочный прогон

`scripts/load_ingest.py` — локально, на своей PostgreSQL: API — отдельный
процесс uvicorn, воркеры `operational` и `ai` — в процессе скрипта; модель —
фейковый провайдер с логнормальной задержкой (медиана 5 с, как у production:
p50 5,2 с в P6), MAX — записывающий двойник и недоступный адрес API (внешние
сервисы не вызывались). Настройки окна — как в production: тишина 30 с, до 6
реплик. Сценарий: **50 чатов × 12 реплик** за ≈ 2,5 мин (600 вебхуков),
в каждом чате ветка о поломке и бытовые реплики, в каждом десятом — реплика
об опасности (газ).

Машина: Windows 11, AMD64 (12 логических ядер), Python 3.12.14, PostgreSQL
16.10 в Docker Desktop на той же машине.

| Метрика | 1 процесс AI-пула (как в production сейчас) | 4 процесса AI-пула |
|---|---|---|
| Приём вебхука, p50 / p95 / max | 33 / 58 / 460 мс | 35 / 76 / 651 мс |
| Ошибки вебхука | 0 из 600 | 0 из 600 |
| Окон разбора / вызовов модели | 105 / 43 | 105 / 105 |
| Окна, разобранные правилами по сторожу (модель не успела за 90 с) | 62 | 0 |
| Окно закрыто → разбор завершён, p50 / p95 | 90,3 / 95,5 с | 21,9 / 30,3 с |
| Окно закрыто → первый сигнал, p50 / p95 | 90,3 / 91,9 с | 22,8 / 30,2 с |
| Пик очереди AI-пула / операционного пула | 79 / 4 задачи | 22 / 4 задачи |
| Ожидание задач операционного пула (тик окна, сторож, оповещение), p95 | ≤ 0,78 с | ≤ 0,71 с |
| Памятки опасности в чат: принято MAX-двойником, от создания до принятия p95 | 5 из 5, 0,09 с | 5 из 5, 0,07 с |
| Весь поток обработан за | 244 с | 217 с |

Сырые JSON прогонов (машина, условия, очередь раз в 10 с) — вывод скрипта; в
репозиторий не кладутся.

**Выводы.**

- **Приём не узкое место.** 600 вебхуков за 140 с — p95 58–76 мс при одном
  процессе API, ни одной ошибки; MAX ждёт ответ до 30 с.
- **Уведомления не задерживаются моделью.** Операционный пул (окна, сторож,
  оповещения, памятки в чат) ждёт меньше секунды даже при очереди AI в 79
  задач: пулы разделены по виду задачи (v3 §10), доставка — только в
  операционном пуле.
- **Пропускная способность — модель.** Один процесс AI-пула разбирает окна
  последовательно: ≈ 1 окно за 5 с, ≈ 700 окон в час. Всплеск в 105 окон за
  2,5 мин (≈ 2 500 в час — в десятки раз выше реального) один процесс не
  догоняет, и сторож через 90 с отдаёт окно правилам: сигналы и опасность не
  теряются, теряется только уточнение моделью. Четыре процесса разбирают всё
  моделью за p95 30 с.
- **Реальная нагрузка.** Загруженный реальный чат — 6,7 окна в сутки в
  среднем, 21 в загруженный день (D1-агрегаты). 100 таких чатов — ≈ 670 окон
  в сутки, ≈ 1 ч работы одного процесса AI-пула в сутки; на вечерние пики —
  второй процесс. Масштабирование — число процессов `ai-worker` (задачи
  забираются с арендой, двойного разбора нет), без изменения кода.
- **Ограничения прогона.** Модель фейковая (задержка как у production, ответ
  «сигналов нет» — поэтому сигналов при разборе моделью меньше, чем у правил);
  MAX — двойник; API, воркеры и PostgreSQL — на одной машине разработчика.
  Это оценка поведения очередей, а не измерение ёмкости production-сервера.

## Лимиты MAX API и очередь

- `POST /messages`: «до 2 сообщений/с в один диалог/группу/канал» (сверка
  документации — [MAX_LIVE_SMOKE](MAX_LIVE_SMOKE.md#методы-max--документальная-сверка-18092026)).
  Соблюдает общий шлюз адресата `max_destination_limits`: одна отправка на
  адресата за раз, следующая — не раньше разрешённого времени, для всех
  процессов через PostgreSQL.
- Общего числового предела запросов в документации нет — только «`429` —
  превышено количество запросов». Отправитель обрабатывает 429/5xx/таймаут
  повторами с растущей паузой; неизвестный исход не повторяется вслепую
  (`unknown`), чтобы не отправить дважды.
- Webhook MAX ждёт ответ не дольше 30 с и повторяет доставку: приём только
  пишет реплику и окно и отвечает за десятки миллисекунд (см. прогон), вся
  работа — в очереди.
- Больше воркеров не повышает лимит платформы MAX: рост числа чатов
  упирается в модель и в шлюз адресата, а не в число процессов API.

## Ограничения и риски

- **Правовая применимость.** Чтение домового чата ботом стороннего сервиса
  требует согласия администратора и владельца чата, основания обработки
  сообщений и поручения обработки; для пилота это отдельный gate
  ([v3 §12](../Claude%20outputs/DOMSIGNAL_TARGET_ARCHITECTURE_v3.md)). На
  хакатоне — только тестовые и синтетические данные.
- **Gate провайдера модели для реальных чатов.** Через polza.ai текст окна
  уходит вышестоящему провайдеру; для реальных чатов нужен провайдер с
  приемлемыми условиями обработки персональных данных (размещение в РФ или
  договор поручения). Смена — конфигурацией, код не меняется.
- **Модель — узкое место пропускной способности**, а не приём: один процесс
  AI-пула разбирает окна последовательно. Горизонталь — несколько процессов
  `ai-worker` (задачи забираются с арендой, без двойного разбора); дневной
  бюджет вызовов защищает расходы, сторож отдаёт окно правилам, если модель
  не успела.
- **Чаты одного бота.** Предел числа чатов у одного бота MAX не подтверждён;
  квота УК — наше правило, не лимит MAX.
- **Регион Москва.** Недоступность «Госуслуги. Решаем вместе» в Москве —
  данные владельца (скриншоты 20.09); на публичных страницах ПОС 24.09 это
  не найдено. Канал «Наш город» сверен по страницам портала.
