# ДомСигнал — масштабирование

Коротко: что одинаково для всех, что меняется от города к городу и от УК к
УК, как подключаются регион и УК, сколько это стоит, что показали нагрузочные
прогоны и реальные чаты и где пределы. Состояние на 27.09.2026 (срез D5);
главное о росте по объёму — раздел [«До 5 000 чатов»](#до-5-000-чатов).

**Формулировка без преувеличений.** Новый регион подключается пакетом данных
и профилями домов; код ядра, роутер и интерфейсы не меняются — это проверено
тестом по всем пакетам (`tests/unit/test_d4_region_packs.py`) и commit-ом,
который добавил два региона без изменений `src/`. RU-PSK и RU-PRI — каркас с
минимумом проверенных каналов, а не «работает во всех регионах».

## Ядро и переменная часть

| Ядро — один код для всех | Переменная часть — данные и настройки |
|---|---|
| Доступ: УК → дом → объект → действие; житель по участию в чате или открытому доступу | **Пакет региона** `regions/<код>`: название, часовой пояс (IANA), каналы, органы, правила маршрута с источниками. Четыре пакета — RU-TA, RU-MOW, RU-PSK, RU-PRI — данными, без `if region` ([REGIONS-AS-DATA](decisions.md#regions-as-data-2026-09-27)) |
| Приём реплик, окна, правила опасности в транзакции приёма | **Профиль дома**: регион, муниципалитет, территория (`uk` / `municipal` / `mixed`) — задаётся при одобрении дома платформой из загруженного справочника ([HOUSE-REGION](decisions.md#house-region-2026-09-27)) |
| Тихие часы, час сводки, сутки дашбордов, время в сообщениях сотрудникам | **Пояс** — из пакета региона дома; у УК — пояс большинства её домов ([REGION-TIMEZONE](decisions.md#region-timezone-2026-09-27)) |
| Сигналы, заявки УК, проверка результата жителями, аудит | **УК**: заявка, одобрение, **квота чатов**, сотрудники и назначения на дома |
| Роутер ответственности, карточка следующего шага, черновик обращения | **Чаты**: подключение A-07 с проверкой прав в MAX, чтение включается у привязки |
| Очередь задач в PostgreSQL, пулы `operational` и `ai`, доставка через outbox | **Провайдер модели**: `LLM_PROVIDER`, профиль модели, дневной бюджет, выключатель `PASSIVE_LLM_ENABLED` |

Новый город — новый каталог `regions/`, профиль его домов и проверка
`scripts/validate_region_pack.py` (валидатор не пропустит канал, недоступный
в регионе пакета, и несуществующий часовой пояс). `route_preview
--compare-regions` печатает колонку на каждый пакет из `regions/` — один код,
разные каналы и основания. `/version` показывает версии загруженных слоёв.

## Как подключить регион — чек-лист

1. **Пакет данных.** `regions/<КОД>/responsibility.yaml`: `layer: region`,
   `region`, `name`, `timezone` (IANA), муниципалитеты с кодами и названиями.
2. **Каналы и правила — только с источником.** `verified` — официальная
   страница органа власти (или самого сервиса), дословная цитата и дата
   проверки; иначе `needs_verification` (запись хранится, жителю не
   показывается). Недоступный в регионе федеральный канал —
   `unavailable_regions` у канала, не код.
3. **Проверка.** `uv run python scripts/validate_region_pack.py` и
   `uv run pytest tests/unit/test_d4_region_packs.py` — десять подтипов дают
   маршрут или честный `unknown`, недоступный канал не предлагается;
   `route_preview --compare-regions` — колонка нового региона.
4. **Второй человек сверяет источники** (открывает каждую ссылку, сравнивает
   цитату и дату).
5. **Выкладка** — обычная (пакеты входят в образ), `/version` показывает
   версию нового слоя.
6. **Дома.** Платформа одобряет заявку УК на дом с регионом из списка
   (без региона — отказ с объяснением); у прежних домов — «Регион не задан» →
   «Задать регион».
7. **УК и чаты** подключаются сами (ниже); разработчики не нужны.

## Порядок тиражирования [оценка]

1. **Пилот:** одна УК в Казани, 3–5 домов с активными чатами, 4 недели.
   Метрики уже считаются в дашбордах D2: доля проблем из чата, дошедших до
   заявки или обращения; время до принятия заявки; доля «это не проблема»;
   отключения бота.
2. **Казань:** ещё 2–3 УК через самостоятельную заявку; ГЖИ РТ как партнёр.
3. **Татарстан:** RU-TA с проверенными каналами («Народный контроль» уже
   проверен и стоит в трёх правилах).
4. **Второй регион по заявке жилнадзора;** кандидат — Псковская область
   (региональный бот, куратор трека из Минстроя Псковской области).
5. **Дальше** — регионы, где жилнадзор администрирует домовые чаты, после
   правового gate ([v3 §12](../Claude%20outputs/DOMSIGNAL_TARGET_ARCHITECTURE_v3.md)).

**Почему эти регионы.** RU-PSK — небольшой регион без своих цифровых кадров;
источник о региональном боте — ИнформПсков, 05.08.2026, вторичный, для
`verified` нужен официальный сайт правительства области. RU-PRI — UTC+10,
проверяет часовые пояса; ГЖИ Приморья сверена по primorsky.ru.

## Как УК подключается сама

1. Страница продукта `/site` (в обычном браузере — и корень сайта) → «Подключить УК».
2. Заявка: организация, ИНН, контакт, **сколько чатов** подключить, адреса.
   Заявитель получает секретную ссылку на страницу статуса.
3. Платформа проверяет организацию, задаёт вопросы (ответ — на той же
   странице) и одобряет с квотой чатов Q.
4. На странице статуса — «Создать аккаунт администратора»: логин, пароль,
   приложение-аутентификатор. Ссылку никто не передаёт вручную.
5. Администратор входит через `/login`, запрашивает управление домами,
   приглашает сотрудников (или платформа открывает регистрацию по ссылке),
   подключает чаты своих домов. Каждый чат — один слот квоты; кончились
   слоты — «Запросить расширение», решение платформы — полностью, частично
   или отказ с причиной ([CHAT-QUOTA](decisions.md#chat-quota-2026-09-26)).
6. Обзоры УК и платформы считают всё по данным базы без текстов жителей.

Окончательная проверка квоты — в транзакции активации привязки под
блокировкой строки УК: две активации за последний слот дают одну
(PostgreSQL-тест гонки из двух и из четырёх активаций).

## До 5 000 чатов

Срез D5, 27.09.2026. Каждое число помечено: **измерено** — прогон или
выгрузка; **расчёт** — расчёт по измеренному (пропускная способность одного
цикла разбора × число циклов, объём реального чата × число чатов);
**оценка** — суждение без измерения. Сырые JSON прогонов — вывод
`scripts/load_ingest.py`, в репозиторий не кладутся; профиль нагрузки и
агрегаты реальных чатов — `evaluation/reports/2026-09-27-*`.

**Формулировка без преувеличений.** Приём и безопасность не зависят от
модели и выдержали 1 000 чатов с потоком в 2 раза выше расчётного пика 5 000
чатов — и на машине разработчика, и на железе production (≈ 0,3 ядра); разбор растёт числом процессов и циклов без
изменения логики (1 → 4 → 8 циклов: 616 → 2 536 → 5 027 окон в час); при
перегрузке система уходит на правила, а не теряет сигналы и памятки. Это
прогоны с моделью-заглушкой (задержка как у настоящей) и записывающим
двойником MAX, а не «готово к 5 000 чатов в production».

1. **Дневной бюджет модели** — это настройка, а не предел: при 500 вызовах в

   минуту (окно ≈ 6,1–6,3 тыс. входа и до 1 600 ответа) → **≈ 13–15 окон в
   минуту, ≈ 800–900 в час на ключ**; сверх — HTTP 429 и разбор правилами.
   Измерено: 8 параллельных вызовов — 0 × 429 (16 вызовов), но в другом

   стороне провайдера непостоянен. Этого хватает десяткам чатов и пику

   хакатона) 16 параллельных вызовов проходили без 429. Дальше — лексический фильтр до модели (пропустил бы

3. **Соединения PostgreSQL** — при 6 и больше процессах по 15 соединений
   нужен PgBouncer (раздел ниже).

   рассылки: рассылка 5 000 чатам — ≈ 11 минут; личные уведомления и
   опасность идут раньше рассылок.
5. **Число чатов у одного бота MAX** не подтверждено документацией — вопрос
   организаторам; реестр чатов строится из событий `bot_added`, ограничение
   выдачи «последние 1 000 чатов» его не затрагивает.

### Пул соединений и PgBouncer

`DB_POOL_SIZE` + `DB_MAX_OVERFLOW` — соединений на процесс (по умолчанию
5 + 10). Правило: **процессы × (размер + запас) ≤ `max_connections`** (100 в
PostgreSQL по умолчанию) минус запас на миграции и копии. Production — три
процесса × 15 = 45. Когда процессов шесть и больше или нужен второй сервер
приложений — PgBouncer в режиме transaction перед PostgreSQL: SQLAlchemy
держит короткие транзакции, а задачи забираются `FOR UPDATE SKIP LOCKED` в
одной транзакции, что с transaction-режимом совместимо. Цикл воркера занимает
не больше одного-двух соединений за раз (вызов модели идёт вне транзакции),
поэтому воркер не стартует, если циклов больше, чем соединений пула минус одно.

## Регион за одну команду

```
python -m domsignal.tools.region_pack new RU-SVE --name "Свердловская область" \
  --timezone Asia/Yekaterinburg --municipality ekb:Екатеринбург
```

Команда создаёт `regions/RU-SVE/responsibility.yaml`: пояс, муниципалитеты,
запись жилнадзора `needs_verification`, правил нет. Валидатор
(`scripts/validate_region_pack.py`) и параметризованный тест
(`tests/unit/test_d4_region_packs.py`) подхватывают пакет без правки кода;
до проверки данных дома региона видят федеральный слой. Дальше — чек-лист
выше: официальные каналы с цитатой и датой, проверка вторым человеком,
выкладка. Готовность каждого пакета (проверено, ждёт сверки, старше 180 дней,
недоступные в регионе каналы) — на обзоре платформы.

**Регион без проверенных данных — Псков.** 27.09 повторная попытка найти
официальную страницу Министерства регионального контроля и надзора
Псковской области о чат-боте в MAX не дала источника: pskov.ru по-прежнему
отвечает HTTP 403, на доменах Госвеб (`*.gosuslugi.ru`) такой страницы нет.
Поэтому записи RU-PSK остаются `needs_verification`: регион работает на
федеральном слое (ПОС, 112, заявка УК, честное «ответственный не определён»),
жителю не обещается канал, который нельзя проверить. Когда появится
официальная страница — запись переводится в `verified` одной правкой данных.

## Дома УК — пачкой

При одобрении заявки УК адреса из неё становятся заявками на дома;
администратор УК может вставить список до 200 адресов; платформа одобряет

## Лимиты MAX API и очередь

- `POST /messages`: «до 2 сообщений/с в один диалог/группу/канал» (сверка
  документации — [MAX_LIVE_SMOKE](MAX_LIVE_SMOKE.md#методы-max--документальная-сверка-18092026)).
  Соблюдает общий шлюз адресата `max_destination_limits`: одна отправка на
  адресата за раз, следующая — не раньше разрешённого времени, для всех
  процессов через PostgreSQL.
- Общего числового предела запросов в документации нет — только «`429` —
  превышено количество запросов». Отправитель обрабатывает 429/5xx/таймаут
  повторами с растущей паузой; неизвестный исход не повторяется вслепую
  (`unknown`), чтобы не отправить дважды.
- Webhook MAX ждёт ответ не дольше 30 с и повторяет доставку: приём только
  пишет реплику и окно и отвечает за десятки миллисекунд (см. прогон), вся
  работа — в очереди.
- Больше воркеров не повышает лимит платформы MAX: рост числа чатов
  упирается в модель и в шлюз адресата, а не в число процессов API.

## Ограничения и риски

- **Правовая применимость.** Чтение домового чата ботом стороннего сервиса
  требует согласия администратора и владельца чата, основания обработки
  сообщений и поручения обработки; для пилота это отдельный gate
  ([v3 §12](../Claude%20outputs/DOMSIGNAL_TARGET_ARCHITECTURE_v3.md)). На
  хакатоне — только тестовые и синтетические данные.
- **Gate провайдера модели для реальных чатов.** С M1 текст окна уходит в
  Cloud.ru, а Qwen3-30B-A3B там — «внешняя» модель: данные передаются вне
  инфраструктуры Cloud.ru. Для реальных чатов нужен провайдер с приемлемыми
  условиями обработки персональных данных (внутренняя модель Cloud.ru — в 7–13
  раз дороже — или договор поручения). Смена — конфигурацией, код не меняется.
- **Модель — узкое место пропускной способности**, а не приём: один процесс
  AI-пула разбирает окна последовательно. Горизонталь — несколько процессов
  `ai-worker` (задачи забираются с арендой, без двойного разбора); дневной
  бюджет вызовов защищает расходы, сторож отдаёт окно правилам, если модель
  не успела.
- **Чаты одного бота.** Предел числа чатов у одного бота MAX не подтверждён;
  квота УК — наше правило, не лимит MAX.
- **Регион Москва.** Недоступность «Госуслуги. Решаем вместе» в Москве —
  данные владельца (скриншоты 20.09); на публичных страницах ПОС 24.09 это
  не найдено. Канал «Наш город» сверен по страницам портала.

### Оставшиеся ограничения — описаны, не сделаны

- **ФИАС/ГАР у дома и импорт «дом → УК» из ГИС ЖКХ** — дом создаётся по
  адресу заявки, профиль задаёт платформа.
- **Пояс на уровне дома** — пояс берётся из региона; внутри региона с
  несколькими поясами (например, Якутия) понадобится поле у дома или у
  муниципалитета.
- **Форма исправлений справочника для УК и ГЖИ** — правки идут через
  репозиторий и выкладку.
- **Лексикон правил только русский.**
- **Российский провайдер модели** — gate пилота (см. выше).
- **Предел чатов у одного бота MAX не подтверждён.**
- **Псковская область** — каналы записаны, но не проверены: сайт
  правительства области недоступен с наших адресов.
