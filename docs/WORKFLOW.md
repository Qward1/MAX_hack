# ДомСигнал — рабочий процесс

Команды ниже подходят для Git Bash, macOS и Linux; приведённые команды Git также выполняются в PowerShell без Bash-подстановок. В примерах всегда выбирайте буквальное имя своей ветки.

## START / SYNC

1. Проверь checkout и дерево: `git rev-parse --show-toplevel`, `git branch --show-current`, `git status --short`. Не переключай ветку при чужих или непонятных изменениях.
2. Один раз выполни `git fetch origin --prune`. Если сеть недоступна, локальная работа возможна, но свежесть ветки коллеги и совместимость не подтверждены.
3. При чистом дереве синхронизируй только собственную ветку: DEV-A — `git merge --ff-only origin/dev/a-core`, DEV-B — `git merge --ff-only origin/dev/b-experience`. Если local и remote разошлись, останови автоматическую синхронизацию и выясни источник; историю не перезаписывай.
4. В своей ветке подтяни только принятую работу: `git merge --no-edit origin/main`. При конфликте согласуй смысл; не применяй массово `ours` или `theirs`.
5. Прочитай handoff коллеги из remote ref без merge: DEV-A — `git show origin/dev/b-experience:docs/status/dev-b.md`, DEV-B — `git show origin/dev/a-core:docs/status/dev-a.md`.
6. Проверь затронутые контракты. После реального merge запусти релевантные тесты; пустой fetch не требует полного прогона.

## PUSH — сохранить свою работу

Просмотри `git status --short`, `git diff` и `git diff --check`. Явно добавь только нужные пути (`git add <path>...`), проверь `git diff --cached` и отсутствие секретов, обнови собственный handoff, затем создай содержательный commit.

Перед push ещё раз проверь `git branch --show-current`. DEV-A отправляет только `git push origin HEAD:dev/a-core`, DEV-B — только `git push origin HEAD:dev/b-experience`. Этот preflight не является серверным ACL.

Незавершённый безопасный checkpoint разрешён как WIP в своей ветке и Draft PR с честным status. Это не готовность к `main`. На активной ветке держи один интегрируемый срез; следующую параллельную задачу размещай в отдельном локальном worktree.

## MAIN — то, что пользователь может назвать «push в main»

Это PR, а не прямой push:

- Выполни fetch, merge актуального `origin/main` в ветку автора и релевантные проверки.
- Открой PR из своей ветки в `main`; укажи task ID, контракты/миграции, проверки и ручную проверку.
- Агент-ревьюер ищет дефекты, но не подменяет approval второго разработчика своим аккаунтом.
- Требуются один approve второго разработчика, resolved conversations и актуальный зелёный `quality-gate`.
- Зафиксируй проверенные head SHA и base SHA. Для CLI: `gh pr merge <PR-number> --merge --match-head-commit <checked-head-sha>` без `--admin` и без удаления постоянной ветки ([W8](https://cli.github.com/manual/gh_pr_merge)).
- При изменении head/base снова проверь условия; строгая защита `main` должна блокировать устаревший результат.
- После merge автор делает fetch и обычный merge `origin/main` в свою ветку; коллега подтягивает `main` в следующей сессии.

После approval не добавляй несвязанную работу. Если `main` сломан, определи проблемный merge и подготовь PR с исправлением или контролируемым revert; не force-reset и не откатывай БД автоматически.

## PEER-CHECK — проверка будущего объединения

Не запускай постоянно. Проверка нужна перед изменением общего контракта, при пересечении файлов или почти одновременной готовности двух PR.

1. Один раз выполни fetch и запиши SHA: `git rev-parse origin/main`, `git rev-parse origin/dev/a-core`, `git rev-parse origin/dev/b-experience`.
2. Для текстовой проверки используй `git merge-tree --write-tree <own-commit> <peer-commit>`; команда не меняет index и рабочее дерево. Сначала проверь `git merge-tree -h`; отсутствие режима не запрещает работу ([W5](https://git-scm.com/docs/git-merge-tree)).
3. Для реальной совместимости создай отдельный временный worktree от записанного main: `git worktree add --detach ../domsignal-peer-check <main-sha>`. В нём последовательно выполни `git merge --no-edit <own-sha>` и `git merge --no-edit <peer-sha>`, затем интеграционные проверки.
4. Если коллега не готов, отметь результат как информативный и не блокируй независимый PR.
5. Не push смешанную ветку и не переноси её в `main`. Не используй общие dev-БД, порты, MAX-токен или volumes. После проверки удали только созданный worktree: `git worktree remove ../domsignal-peer-check`; не применяй `--force` к неизвестным файлам.

Успешный Git-merge не проверяет схему БД, enum, UX и семантику. После двух PR полный тест итогового `main` остаётся обязательным.

## END — конец рабочей сессии

Сделай безопасный checkpoint, fetch и, при чистом дереве, merge `origin/main`; проверь затронутое; обнови handoff до финального commit; push только своей ветки по процедуре PUSH. Незавершённая работа получает честный WIP/блокер, а не ложный DONE.

Сообщи в 3–5 строках: что сделано, что проверено, что нужно коллеге, следующий шаг. Не создавай отдельные отчётные файлы.

END выполняется по команде «заверши день» или при завершении активной рабочей сессии. Не создавай cron, автопуш по времени и unattended-изменения без отдельного запроса.

## AGENTS / WORKTREES

Обычно работает один ведущий агент на разработчика. При реальном выигрыше допустимы до двух пишущих агентов в непересекающихся локальных worktree и один read-only reviewer. Число агентов не увеличивает человеческую способность проверить результат.

Постоянные remote-ветки только три: `main`, `dev/a-core`, `dev/b-experience`. Для параллельных агентов допустимы временные локальные `agent/a/<task-id>`, `agent/b/<task-id>` или detached worktree с сохранённой ссылкой на commit. Владелец последовательно переносит проверенные commits/патчи в свою ветку; автоматически публиковать task-ветки не нужно.

Одну ветку нельзя одновременно checkout в двух worktree и нельзя обходить ограничение `--force` ([W4](https://git-scm.com/docs/git-worktree)). На разных устройствах также действует один active writer постоянной ветки. Compose project, БД/volumes, порты и ignored local data разделяются; production `.env` не копируется.

Делегированному заданию достаточно: task ID, цель, разрешённые пути, входные DTO, acceptance criteria, команды проверки и запрет правки чужих зон. Полный план продукта в каждый prompt не копируется.

## Короткие команды человеку

- «Начни задачу `<ID>` как DEV-A/DEV-B; выполни START и работай до acceptance criteria».
- «Заверши день: END, сохрани изменения и push только моей ветки».
- «Подготовь PR в main по MAIN, но не обходи review/CI».
- «Проверь совместимость с веткой коллеги по PEER-CHECK, не меняя наши рабочие ветки».
