# ДомСигнал — ручные приёмочные тест-кейсы

**Версия набора:** 1.1 от 29.09.2026.
**Проверяемая версия:** коммит под тегом `online-submission-final`; production отдаёт тот же коммит в `/version`.

**Кому:** тестировщику, который не знаком с проектом и не читает исходный код.

**Как пользоваться документом:**
1. Прочитайте разделы 1–5: окружения, подготовка, аккаунты, адреса и порядок прогона.
2. Выполняйте тест-кейсы по порядку номеров: более поздние кейсы используют данные, созданные ранее. Зависимости указаны в поле «Начальные условия».
3. Результат каждого кейса записывайте в журнал прогона по шаблону из раздела 5.4.
4. Всё, что расходится с ожидаемым результатом, — дефект. Запишите: номер кейса и шага, что ожидалось, что получилось, снимок экрана, время по МСК.

Короткий набор перед показом комиссии — [`SMOKE_TEST_CASES.md`](SMOKE_TEST_CASES.md). Способ проверки и автотесты каждого кейса — [`ACCEPTANCE_MATRIX.md`](ACCEPTANCE_MATRIX.md), результаты прогона — [`ACCEPTANCE_RUN_2026-09-29.md`](ACCEPTANCE_RUN_2026-09-29.md). Замечания приёмки и их состояние — раздел 7.

## 1.2 ЛОК — локальный стенд

Нужны Docker Engine или Docker Desktop с Compose v2, браузер Chrome или Edge и приложение-аутентификатор на телефоне (Google Authenticator, Яндекс Ключ, Microsoft Authenticator). Вместо телефона можно использовать команду из SETUP-L4.

> `compose.yaml` передаёт локальный ключ `AUTH_MFA_ENCRYPTION_KEY` для `APP_ENV=local`, вход сотрудника на локальном стенде работает без дополнительных файлов. SETUP-L1 можно пропустить: тогда `dc` ниже — просто `docker compose`. Если файл `compose.qa.yaml` уже создан, он не мешает.

### SETUP-L1. Файл с ключом MFA

1. Откройте терминал в корне репозитория (папка `domsignal-repo`).
2. Соберите образ:
   `docker compose build`
3. Сгенерируйте ключ:
   `docker compose run --rm --no-deps api python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`
   Скопируйте напечатанную строку (44 символа, оканчивается на `=`).
4. Создайте в корне репозитория файл `compose.qa.yaml` и вставьте ключ вместо `ВСТАВЬТЕ_КЛЮЧ`:
   ```yaml
   services:
     api:
       environment:
         AUTH_MFA_ENCRYPTION_KEY: "ВСТАВЬТЕ_КЛЮЧ"
   ```
5. Если в корне уже есть свой файл `.env`, откройте его. Удалите или закомментируйте строки `API_PORT`, `PASSIVE_*`, `DISPLAY_TIMEZONE`, иначе стенд будет вести себя не как описано.

### SETUP-L2. Запуск

1. `docker compose -f compose.yaml -f compose.qa.yaml up -d`
2. `docker compose -f compose.yaml -f compose.qa.yaml ps`. Ожидается:
   - `db` — `healthy`;
   - `api`, `worker`, `ai-worker` — `running`;
   - `migrate` и `seed` — `exited (0)`.
3. Откройте `http://localhost:8000/ready`. Ожидается `{"status":"ready"}`.

**Адрес открывайте именно как `http://localhost:8000`, не `127.0.0.1`.** Кабинет сверяет адрес страницы с `PUBLIC_BASE_URL=http://localhost:8000`. С другим адресом вход сотрудника отклоняется ошибкой 403.

Ниже для краткости `dc` означает `docker compose` (или `docker compose -f compose.yaml -f compose.qa.yaml`, если вы выполнили SETUP-L1).

### SETUP-L3. Суперадмин платформы

1. `dc exec api python -m domsignal.tools.employee_auth bootstrap-platform --login-name platform.admin`
2. Ожидается JSON вида `{"user_id": "…", "action": "bootstrap-platform", "temporary_password": "…"}`.
3. Сохраните `temporary_password`: он одноразовый и действует 24 часа.
4. Повторный запуск ответит `Platform superadmin already exists; use audited recovery`. Суперадмин на стенде один.

### SETUP-L4. Код TOTP без телефона

При подключении аутентификатора кабинет показывает строку «Если камера недоступна, введите ключ вручную: XXXXXXXX…». Сохраните ключ. Текущий шестизначный код:

`dc exec api python -c "import pyotp; print(pyotp.TOTP('XXXXXXXX…').now())"`

Код меняется каждые 30 секунд. Один и тот же код дважды не принимается — дождитесь следующего.

### SETUP-L5. Тестовые УК и сотрудники

Нужны для кейсов с быстрым переключением ролей без пароля.

1. `dc run --rm seed python -m domsignal.tools.seed_tickets`
2. Ожидается строка `A16 synthetic roles and 3 houses ready; real organization connection is not verified`.

### SETUP-L6. Сброс локального стенда

Используйте только для своего локального стенда: команда удаляет все его данные.
1. `dc down -v`
2. Повторите SETUP-L2, SETUP-L3 и SETUP-L5.

Обычная остановка без потери данных: `dc down`, запуск — `dc up -d`.

### SETUP-L7. Доступ к базе для технических проверок

`dc exec db psql -U domsignal -d domsignal -c "<SQL>"`

Технические проверки подтверждают результат, но не заменяют проверку в интерфейсе.

### Что локальный стенд проверить не может

Локально по умолчанию MAX выключен (`MAX_TRANSPORT=off`), модель заменена правилами (`LLM_PROVIDER=rules`), чтение чатов выключено. Логику бота, группы, сигналов и памятки можно проверить и локально — в режиме эмулятора MAX (`MAX_TRANSPORT=record`, `scripts/max_emulator.py`; README, раздел «Проверить бота без MAX»), так их проверяет `tests/acceptance`. Вид и поведение в настоящем клиенте MAX проверяются только на ПРОД:
- бот в личке;
- `/report` в группе;
- пассивное чтение и сигналы;
- памятка об опасности;
- посты, правки и кнопки в чате;
- личные рассылки и уведомления;
- подключение чатов.

Кроме того, эти сценарии прогоняет автоматический стенд `scripts/scenario_run.py` (TC-005): API, двойник MAX, имитация ответов модели.

**Действия:**

   `Казань, ул. Приёмочная, 5`
   `Казань, ул. Приёмочная, 5`
   `Казань, ул. Приёмочная, 1`
   `Казань, ул. Приёмочная, 7`

**Финальный ожидаемый результат:** в заявках на дома нет дублей; квота чатов не тронута.

**Критерий PASS:** итоговые числа и причины пропуска совпадают с ожидаемыми, повтор не создаёт вторую заявку.

> Единый номер экстренных служб: 112
> Источник: Федеральный закон от 30.12.2020 № 488-ФЗ «…»

#### Шаг 2. Оповещение оператору
**Кто выполняет:** оператор с MAX, личка с ботом.

**Ожидаемый результат (≤ 10 секунд):**

> Признак найден правилами ДомСигнала по словам жителя.

## Блок P. Асинхронная обработка и устойчивость

> Архитектура: RabbitMQ и Redis в проекте **нет**. Очередь задач (`jobs`) и outbox лежат в PostgreSQL. Их забирают два процесса-воркера:
> - `worker` — операционный пул: доставка в MAX, рассылки, окна чата, сторож правил, очистка;
> - `ai-worker` — пул модели.
>
> Поэтому проверки ниже смотрят таблицы `jobs` и `outbox_messages`, а не брокер.

### TC-092 — Операционный воркер остановлен: рассылка ждёт, после запуска уходит

**Цель:** задачи не теряются при остановке воркера. Путь «UI → задача в PostgreSQL → воркер → результат → жителю» проходит после восстановления.
**Связанный проектный сценарий:** S30, S18.
**Приоритет:** Critical. **Тип:** Integration / Async / Resilience.
**Участники:** тестировщик (терминал), администратор `a16-admin`, житель `a16-resident`.
**Окружение:** ЛОК.

**Начальные условия:** выполнен SETUP-L5; все сервисы запущены.

#### Шаг 1. Остановить воркер
**Действия:** `dc stop worker`, затем `dc ps`.

**Ожидаемый результат:** `worker` — exited; `api`, `ai-worker`, `db` работают.

#### Шаг 2. Отправить объявление
**Кто выполняет:** администратор → «Рассылки» → «Новое сообщение» → «Объявление», заголовок `Проверка очереди: уборка подъезда`, текст `В субботу генеральная уборка подъездов.`, каналы по умолчанию → «Создать черновик» → флажок → «Подтвердить и отправить».

**Ожидаемый результат:** статус остаётся «Запланировано» (не «Отправлено»), кнопка «Отменить отправку».

**Техническая проверка:**
`dc exec db psql -U domsignal -d domsignal -c "select kind, status from jobs where kind='broadcast.send' order by created_at desc limit 1"` → `broadcast.send | pending`.

#### Шаг 3. Житель пока не видит
**Кто выполняет:** житель → `http://localhost:8000/?test_actor=a16-resident&view=news`.

**Ожидаемый результат:** объявления «Проверка очереди…» ещё нет.

#### Шаг 4. Запустить воркер
**Действия:** `dc start worker`, подождите 10–15 секунд.

**Ожидаемый результат:**
- та же задача — `succeeded`;
- у администратора (экран обновится сам) — «Отправлено», доставка в ленту «2»;
- у жителя (экран обновится сам) — объявление в ленте.

#### Шаг 5. Дублей нет
**Техническая проверка:** `dc exec db psql -U domsignal -d domsignal -c "select title, status from broadcasts where title like 'Проверка очереди%'"` → одна строка `sent`.

**Финальный ожидаемый результат:** задача дождалась воркера и выполнилась ровно один раз.

**Критерий PASS:** пока воркер стоит — «Запланировано» и `pending`; после запуска — «Отправлено», объявление у жителя, одна запись.

**Действия:** `dc exec db psql -U domsignal -d domsignal -c "select kind, last_error_code, attempts from jobs where status='failed'"`.

**Ожидаемый результат:** пусто. Каждая строка здесь — дефект: приложите `kind` и `last_error_code`.

#### Шаг 3. Обзор платформы
**Действия:** суперадмин → «Обзор» → «Очередь задач» и «Состояние системы».

**Ожидаемый результат:** «Ошибки задач» — 0; возраст самой старой ожидающей задачи — секунды (не считая периодических).

#### Шаг 4 (ПРОД, администратор сервера). Срок хранения переписки
Проверка обещания `/privacy` и README: сырые реплики чата хранятся не дольше 72 часов.

**Действия:** на VPS в контейнере базы выполните:
`select count(*) from chat_messages where received_at < now() - interval '72 hours';`
Тексты сообщений не выводите.

**Ожидаемый результат:** `0`. Очистка `chat.buffer.purge` запускается каждый час, поэтому допустимы строки не старше 73 часов.

**Критерий PASS:** упавших задач нет, очередь пуста; на ПРОД в буфере нет реплик старше 72 (+1) часов.

### TC-096 — Повтор POST /reports с тем же Idempotency-Key; тот же ключ с другим телом → 409

**Цель:** повторная отправка из-за сбоя сети не создаёт второе сообщение, а подмена тела под старым ключом отклоняется.
**Связанный проектный сценарий:** S31.
**Приоритет:** High. **Тип:** API / Negative.
**Участники:** тестировщик (терминал с `curl`), тестовые сессии ролей.
**Окружение:** ЛОК.

**Начальные условия:** есть `TOKEN` жителя `demo-third`.

| Шаг | Запрос | Ожидаемый результат |
|---|---|---|
| 1 | `curl -s -w '\n%{http_code}\n' -X POST http://localhost:8000/api/v1/reports -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' -H 'Idempotency-Key: qa-report-0001' -d '{"house_id":"00000000-0000-0000-0000-000000000101","category":"waste","description":"Переполнены мусорные баки у второго подъезда"}'` | `201`, JSON с `report_id`, `incident`, `action_card`.
