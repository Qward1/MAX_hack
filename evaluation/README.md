# Оценка AI-ядра

```bash
uv run python evaluation/run_eval.py --provider rules --out evaluation/reports/
uv run python evaluation/run_eval.py --provider fake  --out evaluation/reports/
```

Сети, ключей и PostgreSQL не требуется. Отчёт пишется парой файлов
`<дата>-<провайдер>-<версия правил>.md` и `.json`.

> Наборы `run_eval.py` — синтетические тестовые наборы; их числа служат порогом
> регрессии («стало ли хуже»), а не оценкой качества на живом потоке. Состав и
> происхождение наборов — [datasets/README.md](../datasets/README.md).

## Что измеряется

| Набор | Как прогоняется | Метрики |
|---|---|---|
| `single_messages.v1` | каждое сообщение — окно `group_report` из одной реплики | роль, категория точно и по пересечению, доля определённых подтипов, пропущенные и ложные проблемы, опасность (найдено/ложные), подъезд, recall-гейт E0b |
| `scope_and_danger.v1` | сообщения — окна из одной реплики; окна — как есть | роль, `location_scope`, точность подтипа, поведение правил на контекстной опасности |
| `chat_stream.v1` | поток режется `windowing.py` (120 с тишины / 10 реплик / 300 с возраста / опасность — сразу), к каждому окну прикладываются до 5 предыдущих реплик как контекст | recall значимых реплик (`new_problem`, `me_too`, `more_info`, `objection`), лишние реплики, recall инцидентов, доля потока в Inbox и в Audit Pool |
| `single_messages.v2` | то же, что и v1 | те же метрики; отличается только разметка внешнего маршрута (`datasets/README.md`) |
| `dedup.v1` | каждый запрос — окно из одной реплики с 10 открытыми элементами | верные привязки, привязки не к тому элементу, пропущенные и ложные привязки |

Доли сопровождаются интервалами Уилсона 95 %. `sklearn` не используется.

## Режимы провайдера

- `--provider rules` — модель не вызывается, работает детерминированный «пол».
  Только к этому режиму применяются регрессионные полы.
- `--provider fake` — детерминированный Fake без сети. По умолчанию он
  отвечает «ничего не нашёл», поэтому прогон проверяет ветку модели,
  валидатор и Emergency Fusion (опасность правил переживает молчание модели),
  а не качество разбора. Полы регрессии к нему не применяются.

## Регрессионные полы (режим правил)

| Пол | Порог |
|---|---|
| типичный срез: категория | ≥ 0,95 |
| типичный срез: роль | ≥ 0,95 |
| пропущено проблем | ≤ 8 из 66 |
| ложных проблем | ≤ 2 из 32 |
| срез опасности | 10 из 10 |
| гейт E0b на проблемах | ≥ 64 из 66 |
| поток E0c, вариант C: recall значимых реплик | ≥ 0,70 |
| набор v2: роль | ≥ 0,94 |
| набор v2: пропущено проблем | ≤ 1 из 67 |
| набор v2: ложных проблем | ≤ 0 из 31 |

Полы набора `v2` — это **текущий результат правил**, зафиксированный как порог
регрессии: они отвечают на вопрос «стало ли хуже», а не «хорошо ли это».

Те же полы проверяет `tests/ai/test_regression_floors.py`, поэтому регрессия
ловится обычным прогоном тестов, а не только отдельным запуском оценки.

## Отбор моделей

```bash
LLM_API_KEY=... uv run python evaluation/select_models.py --out evaluation/reports/
```

Единственный скрипт в каталоге, который выходит в сеть. Кандидаты и основание
политики обработки данных для каждого — `candidates.v1.yaml`. Результат:
отчёт `<дата>-p2-model-selection.md`/`.json` и ресурс
`src/domsignal/ai/resources/models.v1.yaml` с моделью по умолчанию и резервами.

- Жёсткий лимит прогона: **не более 300 вызовов и 500 ₽** (`--max-calls`,
  `--max-rub`). На границе скрипт останавливается и пишет отчёт с уже
  полученными числами.
- Без `LLM_API_KEY` скрипт не делает ни одного внешнего вызова: он собирает
  окна, проверяет их сторожем данных и пишет отчёт с пометкой, что прогон
  не выполнялся (`status` в JSON).
- Этап 1 — 20 фиксированных окон (контекстная опасность `sw01–sw05`,
  отрицания, внешние территории, окна потока E0c) с подбором режима схемы.
  Этап 2 — до 3 лучших на 60 стратифицированных окнах.
- Правило выбора: валидный JSON ≥ 98 %, выдуманных цитат ≤ 2 %, контекстная
  опасность найдена не менее чем в 4 из 5 окон `sw01–sw05`, p95 ≤ 10 с, затем
  меньшая цена при качестве в пределах 3 п. п. от лучшего. Это **инженерный
  выбор модели и режима схемы**, а не решение о включении LLM-слоя: оно
  принимается отдельной оценкой на наборах D3/D5 (ниже).

## Оценка модели против правил (23.09.2026)

```bash
uv run python evaluation/d3_build.py                      # D3: исходник → dev/holdout
uv run python evaluation/p6_eval.py --dataset d3_dev --config rules --run dev-rules
uv run python evaluation/p6_eval.py --dataset d3_dev --config <конфиг> --run <имя>
uv run python evaluation/p6_eval.py --summarize evaluation/reports/p6-runs/<имя>.jsonl
uv run python evaluation/p6_eval.py --routes              # роутер на эталоне маршрутов
uv run python evaluation/d1_aggregates.py <каталог выгрузок> --out <файл.json>
```

- `p6_eval.py` — режим модели и режим правил на **тех же** окнах: политика
  окна ядра по умолчанию, каждый диалог — отдельный поток, открытые элементы
  симулируют продукт (сигналы предыдущих окон диалога с видами опасности).
  Сырые записи окон — `reports/p6-runs/<имя>.jsonl`, сводка — рядом. Метрики:
  доля инцидентов с сигналом, доля сигналов-непроблем, точность подтипа,
  территории, подъезда, маршрута от начала до конца (ядро → `core.routing`),
  опасность D3/D5, роли, валидный JSON, выдуманные цитаты, выброшенные поля,
  p50/p95/p99, ₽ и токены (включая рассуждения). Интервалы Уилсона 95 %.
- Все вызовы модели идут через `guard.SliceBudget`: общий лимит этой оценки **700
  вызовов и 300 ₽**, счётчик — `reports/2026-09-23-p6-ledger.json`; место
  резервируется до вызова, на границе прогон останавливается.
- `d1_aggregates.py` — только числа по реальным выгрузкам; тест проверяет, что
  в выводе нет ни одной строки входа и что скрипт не импортирует провайдера.
- `d2_convert.py` — выгрузка сессии «игрового чата» D2 → строки формата D3.

## Сторож данных

`evaluation/guard.py` — общий вход обоих скриптов. Он отказывается читать
любой путь, ведущий в каталог `data/` (реальные выгрузки домовых чатов), и
останавливает прогон на первой строке без `synthetic: true` либо без
проверенной человеком пометки `origin: real_derived_anonymized` с
`reviewed_by` и `reviewed_at`. Правило закрыто тестами
`tests/ai/test_data_guard.py`.

## Воспроизводимость

В JSON пишутся дата, git SHA, версии таксономии/правил/схемы и SHA-256 каждого
набора. Единственное поле, различающееся между прогонами, — `generated_at`.
Времени выполнения в отчёте нет намеренно: оно сделало бы отчёт
невоспроизводимым.

## Реальные чаты и разметка окон (27.09.2026)

Правило работы с реальными выгрузками: читается только маскированный текст,
модели и внешние API реальные тексты не получают
([REALDATA-D5-2026-09-27](../docs/decisions.md#realdata-d5-2026-09-27)).

- `d5_realdata.py` — окна по политике production (тишина 30 с, до 6 реплик,
  300 с, опасность закрывает окно), сообщения и окна в сутки, часы суток,
  интервалы, всплески, правила без модели (опасность, памятки с паузой 30 мин,
  подтипы и роутер RU-TA / kazan / mixed), профиль нагрузки для
  `scripts/load_ingest.py --profile`. Повторный экспорт того же чата
  определяется по отметкам времени и считается один раз. Вывод — только
  числа; `tests/unit/test_d5_realdata.py` проверяет на синтетической выгрузке,
  что строк входа в выводе нет.
- `d5_labeling.py` — выборка окон для разметки: 100 случайных окон на чат
  (зерно 20260927) + до 30 окон на чат со срабатыванием правил опасности
  (все с правом на памятку и случайные с оповещением). Тексты —
  `data/labeling/windows_masked.jsonl` (маскирование `ai.masking` + адреса,
  упоминания, имена; автор — «Житель A/B» внутри окна). `metrics` считает
  доли с интервалами Уилсона 95 % и качество правил; `human-check` делает
  страницу для людей на 50 случайных окон; `kappa` — каппа Коэна между
  основной разметкой (`labels.csv`) и проверкой людьми (`human_labels.csv`).
- `d5_provider_parallel.py` — настоящий провайдер при параллельности 1/4/8 на
  синтетических окнах набора настройки D3 dev; счётчик — `reports/2026-09-27-d5-ledger.json`.

### Инструкция к разметке окна

Одно окно — одна строка `data/labeling/labels.csv`; текст в файл меток не
попадает.

| Поле | Значение |
|---|---|
| `problem` | 1 — в окне сообщают о неисправности или непорядке в доме, во дворе, в подаче коммунальных услуг (включая «у меня тоже», вопрос «у всех нет воды?»); 0 — быт, споры, реклама, общие рассуждения, поведение соседей без неисправности |
| `incident` | общий id для окон об одном и том же случае (дубли); пусто, если проблемы нет |
| `subtype` | код таксономии `ai/resources/taxonomy.v2.yaml`; `danger.fire` — пожар и дым (в таксономии нет) |
| `addressee` | кто решает: `uk`, `municipality`, `rso`, `tko`, `emergency`, `unclear` |
| `danger_now` | 1 — в доме или у дома сейчас (по словам жителей) опасность для людей: газ, дым, пожар, человек заперт; 0 — прошлое, другой дом, учения, дым сигарет, переносный смысл |
| `official_appeal` | 1 — житель пишет, что подал заявку или обращение (УК, ЕДС, «Госуслуги Дом», жилинспекция) |
| `status_question` | 1 — вопрос о ходе решения известной проблемы («когда починят?», «рассеялся ли дым?») |
| `problem_lines`, `problem_authors` | сколько реплик окна и сколько разных авторов говорят о проблеме |

Спорные случаи решаются в пользу 0; метка — суждение по окну, без внешнего
контекста.
