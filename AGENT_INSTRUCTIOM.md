# ДомСигнал: правила совместной разработки

1. Два владельца: DEV-A — `dev/a-core`, DEV-B — `dev/b-experience`; `main` — только через PR. Не пиши и не push в чужую ветку.
2. Перед задачей проверь branch/status. Один раз прочитай `IMPLEMENTATION_CONTEXT.md`, свою задачу из `ROADMAP.md`, свой status и нужные контракты. Не перечитывай весь план без причины.
3. В начале сессии получи свежие refs, если сеть доступна. Смотри status коллеги в его `origin/dev/...`; локальная копия и `main` могут отставать. Не fetch после каждого изменения файла.
4. Один пишущий агент — один worktree. Владелец объединяет результаты своих агентов последовательно. Не запускай параллельные Git-операции в одном checkout.
5. Не трогай чужие изменения, секреты и данные. Не делай force-push, reset --hard, blind stash, глобальный reformat или массовый git add. Грязное дерево сначала разберись и сохрани безопасно.
6. Маленькая законченная задача лучше большого несогласованного diff. Общие DTO, БД, зависимости, конфигурацию и CI меняй согласованно с владельцем; новую инфраструктуру — только с причиной.
7. Бизнес-логика едина для бота и API. Не копируй правила во frontend. Контракт меняй совместимо либо одним согласованным комплектом producer+consumer+tests.
8. Проверяй риск изменения: локально нужные тесты, перед main — CI объединённого результата с актуальным main. Конфликтов Git нет ≠ регрессий нет. Не отключай проверки ради зелёного статуса.
9. Для исправления бага добавь регрессионный тест. Для доступа, статусов, сроков, повторной доставки и миграций проверяй отрицательные ветки. UX проверяй в браузере, а не только сборкой.
10. Не выдавай отметку жителя за проверенную внешнюю регистрацию; тестовые данные и гипотезы — не реальные интеграции, интервью или измерения. Не выдумывай нормы и сроки.
11. На границе задачи обнови свой `docs/status/dev-*.md` ДО commit/push: результат, проверки, блокер, следующий шаг. Не создавай отчёт на каждый шаг и цепочку коммитов «обновил hash после push».
12. В конце рабочей сессии выполни END из `docs/WORKFLOW.md`: безопасный checkpoint, синхронизация с main, проверки, push только своей ветки. Без активной сессии никакого обещанного фонового push.
13. В main вливай только готовый PR обычным merge commit, с одобрением второго разработчика и зелёным актуальным CI. Не используй squash/rebase для постоянных веток и не удаляй их после PR.
14. Локально MAX transport выключен. Не перенастраивай общий webhook, не запускай polling с общим токеном и не сбрасывай чужие demo-сессии.
15. Файл общего контекста обновляет интегратор после значимого слияния/этапа. При изменении курса правь затронутые задачи и одну короткую запись решения, не переписывай весь roadmap.
16. Работай самостоятельно внутри согласованной задачи. Уточнение нужно при блокере, разрушительном действии, смене scope/публичного контракта или чужой зоне; не останавливайся после каждого файла.

По необходимости: `docs/WORKFLOW.md` — Git-операции; `docs/ARCHITECTURE.md` — границы модулей; `docs/CONTRACTS.md` — контракты. Полный источник: `docs/product/domsignal_plan.md`.
