# ДомСигнал: правила совместной разработки

1. Постоянные ветки сохраняются: DEV-A — `dev/a-core`, DEV-B — `dev/b-experience`, `main` — только через PR. Названия веток исторические: фактического Owner определяет явное поле задачи в `ROADMAP.md`, а не префикс ID или имя ветки. Не пиши и не push в чужую ветку.
2. DEV-A специализируется на AI/NLP/ML и пишет backend-код интеллектуальных модулей. DEV-B владеет продуктовым контуром: UI/MAX, bot, public API/contracts, core/services, DB, auth, rules/regions, общим worker/outbox, инфраструктурой и release. Каноническая подробная матрица путей и задач находится в `ROADMAP.md`.
3. Перед задачей проверь branch/status. Один раз прочитай `IMPLEMENTATION_CONTEXT.md`, свою карточку и Owner из `ROADMAP.md`, свой status и нужные контракты. Полный продуктовый план и несвязанные разделы workflow не загружай без причины.
4. В начале сессии получи свежие refs, если сеть доступна. Status коллеги смотри в его `origin/dev/...`; локальная копия и `main` могут отставать. Не fetch после каждого изменения файла и не называй branch-only код состоянием `main`.
5. Один пишущий агент — один изолированный worktree/checkout. Внутри DEV-A параллельны только непересекающиеся provider/evaluation/NLP-срезы; внутри DEV-B — UI, bot и backend с непересекающимися write-paths. Общие contracts, migrations, locks и wiring имеют одного writer; владелец направления объединяет результаты последовательно.
6. Не трогай чужие изменения, секреты и данные. Не делай force-push, reset --hard, blind stash, глобальный reformat или массовый git add. Грязное дерево сначала разбери и сохрани безопасно.
7. На границе AI ↔ product DEV-B проверяет доступ и допустимый scope, DEV-A анализирует только разрешённые данные и возвращает типизированный результат, DEV-B валидирует его, применяет бизнес-правила и выполняет транзакцию. Рабочий manual/deterministic путь не зависит от LLM. Модель не определяет юридическую ответственность, нормативный срок, внешнюю регистрацию или факт устранения.
8. Public DTO/OpenAPI/generated TS, DB/migrations, bootstrap/settings, общие Python и frontend dependencies/locks, Compose/CI/deploy и общий implementation context пишет DEV-B. AI-specific внутренние контракты, providers/prompts, datasets/evaluation и выделенные AI handlers пишет DEV-A; совместимую продуктовую границу оба проверяют. Для общего файла нужен короткий согласованный diff, а не разрешение на каждый файл внутри своей зоны.
9. Бизнес-логика едина для бота и API. Не копируй правила во frontend и не обходи core из bot handlers. Публичный контракт меняй совместимо либо одним согласованным комплектом producer+consumer+generated types+tests.
10. Проверяй риск изменения: локально нужные тесты, перед main — CI объединённого результата с актуальным main. Для доступа, статусов, сроков, повторной доставки и миграций проверяй отрицательные ветки; UX проверяй в браузере. Не отключай проверки ради зелёного статуса.
11. Не выдавай отметку жителя за проверенную внешнюю регистрацию; тестовые данные и гипотезы — не реальные интеграции, интервью или измерения. Не выдумывай нормы, сроки и production-ответ модели при недоступном AI.
12. На границе задачи обнови только свой `docs/status/dev-*.md` до commit/push: результат, проверки, блокер, следующий шаг. Не создавай отчёт на каждый шаг и цепочку коммитов «обновил hash после push».
13. В конце рабочей сессии выполни END из `docs/WORKFLOW.md`: безопасный checkpoint, синхронизация с main, проверки, push только своей ветки. Без активной сессии никакого обещанного фонового push.
14. В `main` вливай только готовый PR обычным merge commit, с одобрением второго разработчика и зелёным актуальным CI. DEV-A обязательно review PR коллеги; роль интегратора DEV-B не позволяет обходить review, protection или `--admin`. Постоянные ветки не squash/rebase и не удаляются после PR.
15. Локально MAX transport выключен. Не перенастраивай общий webhook, не запускай polling с общим токеном и не сбрасывай чужие demo-сессии.
16. DEV-B — интегратор по умолчанию и обновляет `IMPLEMENTATION_CONTEXT.md` после значимого принятого merge/этапа. Реализованное состояние сверяется по указанному main/ref и различает `IMPLEMENTED IN BRANCH`, `MERGED` и `LIVE VERIFIED`; прогресс ветки остаётся в status владельца.
17. Работай самостоятельно внутри согласованной задачи. Уточнение нужно при блокере, разрушительном действии, смене scope/публичного контракта или чужой зоне; не останавливайся после каждого файла.

По необходимости: `docs/WORKFLOW.md` — Git-операции; `docs/ARCHITECTURE.md` — границы модулей; `docs/CONTRACTS.md` — контракты. Историческое обоснование: `docs/product/domsignal_plan.md`.
