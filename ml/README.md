# ДомСигнал: автономный ML/NLP-блок

Готовый автономный консольный блок для сообщений домовых чатов. Ветвь `ml/standalone` создана в отдельной рабочей копии от `origin/dev/a-core` (`d18ee86`). Основной код не менялся. Рекомендуемый вариант использует E5 и дообученный ruBERT; лёгкий вариант работает на CPU. Режимы `single`, `chat` и `eval` запускаются без участия человека и без платного API. Выход — предварительные сведения для аналитики и демонстрации; внешнюю отправку заявок и юридический выбор адресата CLI не выполняет.

## Итоговая поставка: без LLM и API-ключей

Запускаемый из репозитория `ml/cli.py` использует **только локальные ML-модели и правила**. Режимы `single`, `chat`, `replay`, `eval` и `train` не вызывают LLM, не читают API-ключ и не отправляют сообщения в сеть. Для инференса `heavy` загружает E5 и ruBERT только из локального кэша/каталога; если весов нет, проверка `ml/check.py` сообщает об этом. Для установки и работы CLI **не нужен ключ Polza.ai или другого провайдера**. Прямые затраты на API при эксплуатации — **0 ₽**.

Код платного пилота сохранён отдельно в `ml/experiments/06_llm_cascade/` для воспроизводимости исследования. Он не импортируется рабочим CLI, а зависимость для него вынесена в `ml/requirements-llm-pilot.txt`. Локальный файл с ключом в `ml/artifacts/` исключён из Git и не является частью поставки. В другом клоне без этого файла рабочий CLI ведёт себя так же. Веса моделей тоже исключены из Git: на новой машине их нужно подготовить отдельно по инструкциям ниже, но **API-ключ для этого не требуется**.

В ограниченном исследовательском пилоте на 10 заранее выбранных трудных синтетических сообщениях локальная модель совпала со слабой меткой в 2 случаях, Qwen — в 4, gpt-oss-120b — в 5. Это не сопоставимо с метриками на реальном test и **не является качеством поставляемого решения**: измеренного улучшения на независимом реальном чате нет, а автоматическая склейка LLM не подтверждена. При последующей интеграции с основным проектом можно отдельно проверить выборочный LLM-каскад: ключ хранить на сервере вне репозитория и передавать только сервису, который делает запросы. Включать такой каскад стоит после оценки на новом потоке и проверки обработки персональных данных; текущая версия работает полностью без него.

**Итог на отложенном test классификации:** усиленный вариант обнаруживает проблемы с AP **0,900 / 0,829** и даёт macro-F1 всей цепочки **0,669 / 0,571** для WhatsApp / Telegram. На отдельно размеченных ассистентом чатах F1 объединения сообщений в инциденты — **0,354** при precision **0,928**; это предварительная оценка, не независимый человеческий эталон. Слабую экстренность (полнота 0,507) нельзя использовать для автономной тревоги.

**Исследование раунда 3, без изменения CLI:** BM25 и новая многоголовая модель проиграли текущему ансамблю. Дополнительная бинарная голова на замороженном ruBERT повысила macro-F1 на повторно использованной `val` с 0,697 до 0,723, но на ранее просмотренном `test` средний F1 остался 0,620. Малый платный пилот показал возможную пользу LLM только на выбранных трудных сообщениях, но не доказал улучшение реального потока или безопасную автоматическую склейку. Поэтому локальная модель остаётся рабочим вариантом, а все классы и связи — предварительными результатами. Подробности — `docs/RESEARCH_ROUND3.md` и `docs/LLM_CASCADE_PLAN.md`.

| Дополнительная проверка | Результат | Вывод |
|---|---:|---|
| 67 весов/способов смеси на повторной `val` | лучший F1 0,705 против 0,697; парный 95% ДИ разницы пересекает ноль | Сохранить смесь 50/50 |
| BM25 + BERT на `val` | F1 0,664 против 0,697 | Не заменять TF-IDF |
| Многоголовый `ruBERT-base`, 2 эпохи, 38,2 мин GPU | F1 0,628 на `val` | Не заменять каскад |
| Новый gate на ранее просмотренном `test` | F1 0,620 против 0,620; AP вырос в обоих чатах | Не менять рабочий порог по повторному тесту |
| Парная модель E5 + признаки связи, 2 ранее просмотренных дня | F1 кластеров 0,552/0,694, но precision 0,398/0,548 | Ложных объединений слишком много |
| Диагностика с идеальными метками одного этапа на уже просмотренном `test` | При идеальном gate F1 0,817/0,796; при идеальном классе только принятых проблем 0,802/0,721 | Это потолки компонентов, не качество обученной модели |

Подробные настройки, ресурсы, интервалы и ограничения этих сравнений — в `docs/RESEARCH_ROUND3.md`. Платный пилот описан там же; LLM **не входит в итоговый `single/chat/eval`**.

## Запуск на этой машине

Команды выполняются из `C:\Users\Dimentiy\repoVScode\MAX_hack_ml_standalone`. Локальные веса уже лежат в `ml/artifacts/`; они исключены из Git. Нужен Python 3.10+. Установите зависимости один раз и проверьте комплектность без сетевого запроса:

```powershell
python -m pip install -r ml/requirements-embeddings.txt
python ml/check.py --engine heavy --data-root ..\MAX_hack\datasets
```

**Рекомендуемый вариант с лучшей измеренной классификацией:**

```powershell
python ml/cli.py single --engine heavy --text "В подъезде нет горячей воды"
python ml/cli.py chat --engine heavy --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl
python ml/cli.py eval --engine heavy --split test --data-root ..\MAX_hack\datasets --output ml/artifacts/my_eval.json
```

Вымышленный пример `chat` создаёт заявку `case-1`, присоединяет второе сообщение и помечает восстановление услуги как `resolution_pending_human`. Это последнее состояние не блокирует обработку чата: программа продолжает работу, а заявка остаётся открытой. `chat` и `replay` принимают по одному JSON-объекту на строку из файла или stdin и выдают один результат на строку; обязательное поле — `text`, для нормальной склейки нужны `id`, `ts` в ISO 8601 и `house_id`, при ответе полезен `reply_to`. Состояние заявок хранится только до завершения процесса. `single` может читать сообщение из stdin без `--text`. `eval` пишет только агрегаты, без текстов; указанный `--output` не перезаписывает сохранённые результаты экспериментов.

Если GPU или тяжёлые веса недоступны, используйте **лёгкий CPU-вариант**: установите `ml/requirements.txt`, выполните `python ml/check.py --engine light`, затем `python ml/cli.py single --engine light --text "..."` или `python ml/cli.py chat --engine light --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl`. Если `light.joblib` отсутствует после переноса репозитория, создайте его командой `python ml/cli.py train --variant best --data-root <путь-к-datasets-v3.0>`. В этой рабочей копии обучать заново не нужно. Для тяжёлого варианта на другой машине нужны скачивание открытых весов и обучение по инструкциям ниже; файлы весов не входят в Git. Дополнительные CatBoost и LightGBM нужны лишь для повторения сравнений из `ml/requirements-experiments.txt`.

Выход `single` содержит `is_problem`, `fine_class`, продуктовую категорию и подтип, `recipient_hint`, тип реплики, экстренность, оценки модели и слоты подъезда/этажа. `recipient_hint` — тип маршрута, а не проверенная организация; `product_subtype_suggestion=null` означает недостаток данных для подтипа. `requires_human_confirmation` и `urgent_human_review` — **информационные флаги**, они не требуют ручного шага для работы CLI. Без оператора не используйте эти результаты для автоматической отправки или закрытия реальных заявок: уверенность класса не калибрована, а экстренная модель пропускает часть событий.

## Схема

1. **Граница проблемы:** лёгкий вариант использует TF-IDF по символьным 2–5-граммам и словесным 1–2-граммам с логистической регрессией. Усиленный вариант добавляет замороженные эмбеддинги multilingual-E5 к TF-IDF. Оба обучены на реальных `train` плюс 735 синтетических записей, явно допущенных полем `annotation.use` для gate. Пороги выбраны только на общей реальной `val` при целевой точности 0,80.
2. **Класс и тип сообщения:** лёгкий вариант использует отдельную линейную голову класса. Усиленный вариант смешивает её оценку 50/50 с головой дообученного на известных проблемах `ruBert-base`; вес выбран на `val`. Метка остаётся одной из 33 L3; отображение в пять продуктовых категорий и 31 подтип описано в `configs/class_mapping.yaml`. Тип реплики остаётся у лёгкой модели; `resolved_notice` дополнительно проверяется узким словарным правилом.
3. **Экстренность:** отдельный классификатор на `safety/train`; порог выбран на `safety/val` при доле ложных тревог не более 5%. Явные признаки риска дают отдельный `urgent_human_review`, даже если модель экстренности не подняла флаг. Этот признак не считается доказательством чрезвычайной ситуации. Экстренный флаг **не** превращает сообщение в заявку без подтверждения границы проблемы: на `val` это почти не повышало полноту и снижало точность.
4. **Склейка:** внутри одного дома проверяются класс, подъезд, объект (например, грузовой/пассажирский лифт), окно 24 часа, `reply_to` и пересечение слов. Опциональное правило `service_context_6h` объединяет общедомовые отключения между подъездами в пределах шести часов и не закрывает их без оператора. Плановое объявление не открывает заявку. Решения о создании и закрытии помечаются предварительными.

Разбор существующего решения — `docs/CURRENT_SOLUTION.md`; расхождения таксономий — `docs/CLASS_MAPPING.md`. В продукте анализируется окно сообщений и несколько сигналов, а в L3 метка относится к одной реплике. Поэтому оценки ниже относятся к этой автономной задаче, а не к качеству существующего оконного LLM.

## Почему выбран этот вариант

Измеренное преимущество усиленной цепочки над лёгкой на test составляет +0,037/+0,051 AP границы и +0,049/+0,058 macro-F1 полной классификации (WhatsApp/Telegram). Есть и практические причины выбора:

| Решение | Дополнительное основание |
|---|---|
| Отдельные gate и голова класса | Проблем всего 9–12%; отдельный gate позволяет управлять потоком ложных заявок. У плоской и многоголовой модели редкие классы конкурируют с многочисленным `not_a_problem`; проверенные варианты были хуже. |
| E5 + символьный/словесный TF-IDF для gate | E5 помогает с переформулировками, символьные признаки устойчивы к коротким репликам и опечаткам. Всё работает локально и не передаёт чат провайдеру. |
| ruBERT + TF-IDF 50/50 для класса | Головы исправляют разные ошибки, в том числе на редких классах; удаление разреженной головы теряет правильные случаи. Плотный подбор другого веса дал неустойчивый выигрыш на уже использованной `val`. |
| Правило `service_context_6h` для демонстрации чата | Учитывает дом, время, подъезд, `reply_to` и общедомовые услуги; дает намного больше правильных связей, сохраняя высокую точность на трёх просмотренных днях. Обученная модель пар транзитивно склеивала разные события. При повышенной цене ложного объединения можно выбрать `conservative`. |
| Локальный режим без LLM в основном CLI | Нет платы за запрос, сетевой задержки и зависимости от доступности API. В малом LLM-пилоте были ошибки формата и недостаточная точность связи; доказанного выигрыша в реальном потоке пока нет. |

Усиленная модель требует около 2,3 ГБ RAM и 1,8 ГБ выделенной видеопамяти при инференсе на измеренной GTX 1650; p50 тёплого одиночного сообщения — 33,5 мс. Лёгкая CPU-модель занимает около 247 МБ RAM и даёт p50 8,1 мс. Поэтому при нехватке памяти есть работающий запасной режим, а для лучшего измеренного качества на данной машине рекомендуется `heavy`. Обе модели допускают запуск без новой разметки и без человека в консольном цикле, но не подтверждают фактический адресат, экстренность или устранение проблемы.

## Данные и проверка

Использованы только v3.0: реальные WhatsApp (`train` 3 536, `val` 1 008, `test` 1 765) и Telegram (`train` 13 397, `val` 3 195, `test` 6 147), синтетика только в `train`, отдельный набор safety. Реальные test не смешивались; подбор настроек и порогов проводился на val. Семейства/треды разделены исходным разбиением. Для AP и macro-F1 указан 95% бутстрэп по `family_id`/`thread_id`; интервалы оригинального ориентира рассчитаны обычным бутстрэпом сообщений и не идентичны по методу.

Метки исходного набора классификации получены LLM без проверки человеком. Спорные сообщения исключены, поэтому оценки могут быть оптимистичны для живого чата. Для инцидентов создана отдельная разметка ассистента на 205 сообщениях из трёх дней, но независимого человеческого эталона по-прежнему нет. Сырые тексты, переписки и веса не добавлены в git; веса содержат признаки обучения и остаются локальными.

### Склейка на вручную просмотренных чатах

Ассистент разметил 205 сообщений трёх полных дней на 20 инцидентов **до просмотра предсказаний склейки**. 24 неоднозначных сообщения исключены из основной оценки, 8 сообщений связаны с несколькими инцидентами. Первый день использован для разработки правила; два других (136 сообщений, 10 инцидентов) отложены и проверены один раз после фиксации кода. Это не независимый человеческий эталон, и сообщения могли входить в старые train/val/test классификации.

| Отложенные дни, попарная метрика | Precision | Recall | F1 |
|---|---:|---:|---:|
| Усиленная модель, старое осторожное правило | 1,000 | 0,018 | 0,036 |
| Усиленная модель, широкий порог 6 часов | 0,917 | 0,070 | 0,130 |
| **Усиленная модель, правило общедомовых услуг** | **0,928** | **0,219** | **0,354** |
| Правильные первичные классы сообщений + то же правило, диагностика | 0,920 | 0,977 | 0,948 |

Новое правило доступно через `--merge-policy service_context_6h`. Оно повысило склейку общедомовых отключений между подъездами, но цепочка всё ещё пропускает много коротких контекстных реплик: gate на этих днях нашёл 60 из 99 сообщений с инцидентом. Проверили также объединение решений лёгкого и тяжёлого gate: `OR` дало F1 склейки 0,354, `AND` — 0,328; прироста поверх тяжёлого варианта нет. Подробная методика, ошибки и воспроизведение — в `docs/CHAT_INCIDENT_EVAL.md`; агрегаты без текстов — в `experiments/04_grouping/manual_eval_heldout.json`.

## Задержка и стоимость

### Второй раунд: более сильные классификаторы

Гипотезы были записаны **до** экспериментов в `docs/RESEARCH_ROUND2.md`. Для выбора использована только реальная `val`. Сначала на `test` один раз проверена комбинация gate + ruBERT. После неё на `val` подобран ансамбль класса с лёгкой головой; его также один раз проверили на `test`. Это повторное использование test для нового подхода, поэтому сравнение с первым вариантом следует считать исследовательским, а окончательную оценку подтвердить на новых данных. Macro-F1 полной цепочки считается по всем сообщениям и наблюдаемым истинным меткам, включая `not_a_problem`.

| Подход | Основной результат на `val` WA/TG | Решение |
|---|---:|---|

| Плоские 34 класса, TF-IDF + LR | F1 0,635 / 0,524 | Уступил выбранной цепочке |
| Плоские 34 класса, TF-IDF + ridge / complement NB | лучший F1 0,683/0,558 и 0,579/0,412 | Простые разреженные альтернативы уступили ансамблю |

| Замороженный E5 + линейная голова класса | условный F1 0,792 / 0,657 | Эмбеддинг без дообучения недостаточен |

В одном раннем наборе исследовательских JSON macro-F1 считался по объединению истинных и предсказанных меток, что занижало значения относительно базовой метрики; они не использованы для выбора. Финальные контрольные точки переоценены с тем же правилом, что у базовой линии.

Порог gate 0,5462 выбран на `val`. На `test` он дал точность/полноту 0,8185/0,8244 для WhatsApp и 0,7388/0,7828 для Telegram. Если известно, что сообщение является проблемой, ансамбль класса имеет F1 0,8109/0,7893, но в продуктовой цепочке промах gate превращается в `not_a_problem`. Опубликованный ориентир полной F1 0,640/0,494; усиленный вариант выше на обоих источниках, но интервалы группового бутстрэпа широки и независимой ручной разметки пока нет. Полные PR-кривые и per-class числа — `experiments/02_classes/ensemble_test.json` и консольный отчёт `experiments/eval_hybrid_e5_rubert_sparse_ensemble_test.json`.

Парный бутстрэп по семействам/тредам относительно **нашего лёгкого варианта на тех же сообщениях** даёт прибавку AP +0,037 [0,021–0,056] / +0,051 [0,036–0,068] и полной F1 +0,049 [0,003–0,118] / +0,058 [0,022–0,103] для WA/TG. Он уменьшает шум сравнения, но не устраняет ошибки LLM-разметки и повторное использование test при развитии подхода.

На классах с ≥5 test-примерами остаются слабые места: WhatsApp `security_incident` и `pests` F1 по 0,40 (10 и 7); Telegram `elevator_vandal` 0,20 (6), `other_problem` 0,32 (13), `snow_removal` 0,33 (8), `security_incident` 0,39 (30). Это не повод автоматически менять пороги по test. Тип реплики усиленного варианта остаётся от лёгкой модели и даёт F1 0,559/0,483 на известных проблемах; экстренность не улучшилась: полнота 0,507 при FPR 0,028 на реальном safety/test.

### Проверка на лентах чата

Скрипт `experiments/04_grouping/replay_real.py` восстановил последовательности из обезличенных `all.jsonl` и `excluded.jsonl` для трёх заранее выбранных дней, сохранив порядок сообщений. Эти полные ленты могут включать сообщения из train/val/test, поэтому это **операционная проверка**, а не независимая метрика качества. На тихом дне из 268 сообщений усиленный вариант не создал ни одной заявки. На дне с проблемами в двух чатах (182 сообщения) консервативная склейка создала 39 предварительных заявок; на другом дне (138 сообщений) — 27. По принятой LLM-разметке сообщения gate обнаружил 35 из 45 и 35 из 38 проблем; среди исключённых спорных сообщений модель предложила 12 из 26 и 15 из 35 как возможные проблемы. Эти цифры показывают нагрузку на оператора, а не точность на спорных сообщениях.

Расширение склейки до «тот же класс в пределах 6–24 часов» сократило число заявок до 15 и 11, но собрало вместе сообщения **разных размеченных классов** в 1 и 2 группах; крупнейшая группа включила 14 и 15 сообщений. На слабом наборе пар широкое правило достигает F1=1,000 из-за способа создания самих меток. Для запуска с более полной склейкой явно задавайте `service_context_6h`; CLI сохраняет осторожный `conservative` как стандартное поведение при отсутствии флага. Оценка точности на новых днях неизвестна. Агрегаты без текстов — `experiments/04_grouping/replay_real_heavy.json`.

Контекст соседних реплик не улучшил gate: на `val` Telegram AP упал с 0,862 до 0,836 при добавлении `reply_to` и до 0,609 с двумя предыдущими сообщениями. Эталон классификации помечает отдельную реплику; `reply_to` оставлен только для объединения и закрытия заявки.

### Воспроизведение усиленного варианта

Нужна GTX 1650 4 ГБ или более мощная видеокарта для повторения обучения с приведённым временем. Публичные веса скачиваются один раз, тексты данных при этом не отправляются. Команды ниже выполняются из корня отдельной рабочей копии после обучения лёгкого варианта:

```powershell
python -m pip install -r ml/requirements-embeddings.txt
python -c "from huggingface_hub import snapshot_download; snapshot_download('intfloat/multilingual-e5-base')"
python -c "from huggingface_hub import snapshot_download; snapshot_download('ai-forever/ruBert-base', local_dir='ml/artifacts/models/rubert-base')"
python ml/experiments/03_embeddings/run.py --data-root ..\MAX_hack\datasets
python ml/experiments/03_embeddings/hybrid_gate_sparse_head_val.py ..\MAX_hack\datasets
python ml/experiments/02_classes/train_encoder.py --data-root ..\MAX_hack\datasets --model ml/artifacts/models/rubert-base --name base_positive --mode flat --positive-only --epochs 3 --batch-size 8 --max-length 64 --lr 2e-5
python ml/cli.py single --engine heavy --text "Во втором подъезде нет горячей воды"
```

Дообучение `ruBert-base` заняло 1 353 с (22,6 мин), пик выделенной видеопамяти 3 418 МБ, файл контрольной точки 713 МБ. Получение E5-эмбеддингов train/val/synthetic заняло 87 с, пик 1 142 МБ; обучение гибридного gate с готовым кэшем — 10 с. На GTX 1650 4 ГБ загрузка финального ансамбля заняла 9,47 с, 100 одиночных сообщений после прогрева — 33,51 мс p50 / 48,46 мс p95; пакет из 100 — 73,9 сообщения/с. RSS процесса 2 295 МБ, пик выделенной видеопамяти на инференсе 1 817 МБ. Это локальный замер без сети и интерфейса; обучение и эксплуатация на CPU возможны, но время на CPU не измерено. Прямые API-расходы усиленного варианта также **0 ₽**; стоимость видеокарты, энергии и работы оператора не включена.

Исходный `train_encoder.py` сохраняет все четыре головы, но при `--positive-only --mode flat` обучается и используется только голова класса. Его служебные оценки необученных gate/utterance/safety не следует трактовать как результат. Для отдельных задач работают проверенные лёгкие головы. Калибровка уверенности класса и устойчивость к новым домам остаются открытыми.

Лёгкая модель обучается примерно 14 с на указанном ноутбуке. После загрузки (2,06 с) 500 одиночных сообщений Telegram val обрабатывались за **8,10 мс p50 / 10,19 мс p95**, RSS процесса 247 МБ. Это замер тёплого локального процесса, без диска, UI и сети. Платные API не использовались: прямые API-расходы **0 ₽**; электричество, оборудование и работа оператора не оценены.

В текущем продукте профиль `openai/gpt-5-mini` на 138 **синтетических окнах** показывает ориентир 0,06 ₽ за окно, p50 5,493 с, p95 8,066 с (`docs/CURRENT_SOLUTION.md`). Окно может содержать несколько сообщений; локальные миллисекунды на сообщение нельзя прямо считать ускорением всего продукта. Отдельный ограниченный пилот через Polza.ai выполнил 114 запросов к закреплённым российским провайдерам на 9,1394 ₽ суммарно. Это стоимость исследования, не цена рабочего каскада; данные пилота слишком малы для прогноза частоты ошибок в потоке. Расчёт и технические ограничения — `docs/LLM_CASCADE_PLAN.md`.

## Ошибки и ограничения

- У лёгкого варианта на test слабы редкие классы: `waste_not_collected` (F1=0 на 3 WA и 1 TG), `pests` (0,44 на 7 WA и 0 на 1 TG), `elevator_vandal` (0 на 6 TG), `no_cold_water` (0,40 на 11 TG), `other_problem` (0,43 на 13 TG). При таком числе примеров цифры нестабильны. Полный per-class отчёт — в `eval_best_test.json`; слабые классы усиленного варианта перечислены выше.
- Условный пример ошибки на **вымышленном** тексте у лёгкого варианта: «Во втором подъезде не работает грузовой лифт» получает верный `elevator_out`, но ложный `emergency=true`. Усиленный вариант на вымышленном «В подъезде не работает лифт» также ошибочно поднял `emergency=true`. «Запах газа в подъезде, срочно!» получает `gas_smell`, но лёгкая модель ставит `emergency=false`; явное правило поднимает `urgent_human_review=true`. Эти примеры проверены через `single`, но не включены в test-метрики.
- Короткие ответы, отрицания, плановые отключения и сообщения «починили» требуют контекста. Метка L3 дана по собственному тексту реплики, поэтому на ней нельзя честно оценить пользу окна для класса. При склейке используется `reply_to`, а новое правило объединяет общедомовые услуги в пределах времени. Короткие реплики без явной связи остаются трудным случаем; автоматическое закрытие остаётся неподтверждённым.
- Классы L3 не кодируют территорию, регион и исполнителя. Даже «точное» отображение подтипа не доказывает адресата. Шесть классов нарушений соседей/парковки/безопасности не создают обычную заявку УК по умолчанию. Без внешних данных об адресе и зоне ответственности адресат остаётся подсказкой.
- Данные двух чатов одного дома и синтетика не доказывают перенос на другой дом или MAX. Разметка не проверена человеком; спорные случаи исключены. Реальные потоки и личные данные нельзя публиковать.

## Дальнейшее развитие без ручной проверки

Следующие числа разделяют **измеренный результат**, **цель следующего цикла** и **диагностический потолок**. Цель — критерий, по которому стоит принимать новый вариант, а не обещанная метрика. В доступном корпусе метки получены LLM; больше таких же меток не превращает оценку в независимую истину.

| Горизонт | Что можно сделать без участия человека | Конкретный результат и его статус |
|---|---|---|
| **Сейчас, без новых ресурсов** | Запустить готовые веса и потоковый CLI командами выше. | **Уже достигнуто на исходном test:** AP 0,900/0,829 и macro-F1 0,669/0,571 (WA/TG); на двух чат-днях pair F1 0,354 при precision 0,928. Это и есть немедленно доступное качество, с оговоркой о слабой разметке. |
| **Когда появится GPU 24–48 ГБ, тот же корпус** | Сразу обучить более крупный русскоязычный/мультиязычный энкодер с длиной 128–256 токенов, калибровать gate и класс раздельно, попробовать LoRA/полное дообучение и 3–5 seed. На той же мощности обучить cross-encoder только для нескольких кандидатов связи. | Модели и эксперименты запускаемы сразу. **Доказанного численного прироста от одной мощности нет:** проверенный многоголовый ruBERT-base проиграл. Практический порог принятия — хотя бы +0,02 macro-F1 на новом отложенном периоде при прежней или лучшей точности gate; ниже этого оставлять текущую систему. |
| **Когда появятся новые чаты и больше данных** | Автоматически разметить новые периоды двумя независимыми LLM-проходами по L3, оставить только согласованные метки, убрать дубликаты по семействам, отдельно собрать редкие классы и 30–50 дней для обучения связей. Проверять результат на более позднем периоде, который не участвовал в отборе. | Кривая обучения на старой `val`: удвоение реальных train с ~8,5 до 16,9 тыс. повысило AP gate примерно на **0,05/0,05**. Для следующего удвоения разнообразных данных плановый, но не гарантированный ориентир — **+0,01–0,03 AP** и **+0,02 macro-F1** полной цепочки: около AP 0,91–0,93/0,84–0,86 и F1 0,69/0,59 относительно текущего test. Качество новых домов может быть ниже. |
| **Крупный корпус нескольких домов + сильное оборудование** | Совместно учить поиск кандидатов инцидента, cross-encoder пары и ограниченную кластеризацию; редкие классы дообучать на разнообразных реальных случаях, а не копиях шаблонов; отдельно обучать экстренность на реальных текущих событиях. | Рабочие **цели проекта**, которые придётся подтвердить на будущем периоде: macro-F1 полной классификации ≥0,75/0,70, pair F1 ≥0,60 при precision ≥0,90 и полнота экстренности ≥0,80 при FPR ≤0,05. Эти числа не следуют из нынешних данных как гарантированный результат; без новых независимых меток их нельзя назвать достигнутыми. |

Диагностика предела текущей архитектуры на уже просмотренном test показывает, где есть резерв. Если **идеально исправить только gate**, сохранив нынешнюю голову класса, macro-F1 стал бы 0,817/0,796. Если идеально исправить только класс у принятых настоящих проблем, сохранив gate и его ложные срабатывания, получилось бы 0,802/0,721. Для склейки на двух небольших днях подстановка правильных первичных меток при нынешнем правиле даёт pair F1 **0,948**. Честно назвать точный «максимально возможный» F1 на будущих домах нельзя: корпус охватывает один дом, редкие классы малы, а спорные сообщения исключены. Математический максимум метрики 1,0 в этих очищенных данных не является инженерной целью.

Пока нет новых данных и проверки результата на новом периоде, этот блок следует использовать для демонстрации, анализа потока и предварительных заявок. Автоматическую отправку или закрытие реальных обращений он не реализует.
