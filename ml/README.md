# ДомСигнал: самостоятельный модуль анализа сообщений

Модуль читает сообщения домового чата, определяет, есть ли проблема, предлагает её вид и адресата, оценивает срочность и объединяет сообщения об одной проблеме в предварительную заявку. Он работает из консоли **отдельно от основного приложения**. Рекомендуемый вариант сочетает три локальные модели; для обычного процессора есть облегчённый вариант. Настоящие заявки приложение пока через этот модуль не создаёт.

## Запуск в чистом клоне без закрытых данных

Набора v3.0 и обученных весов в репозитории нет. Чтобы проверить, что код модуля
работает целиком — обучение, одно сообщение, лента чата, оценка, — используйте
синтетический смоук-набор: его строит `ml/scripts/make_smoke_data.py` из шаблонов
(ни одного реального сообщения) в игнорируемую Git папку `ml/artifacts/smoke-data/`.
Обученная на нём модель знает 10 классов и нужна только для проверки
работоспособности; её числа **не являются оценкой качества**.

```bash
python -m venv ml/.venv            # Windows: ml\.venv\Scripts\python вместо ml/.venv/bin/python
ml/.venv/bin/python -m pip install -r ml/requirements.txt
PYTHONPATH=ml/src ml/.venv/bin/python -m unittest discover -s ml/tests      # 7 тестов объединения и слотов
ml/.venv/bin/python ml/scripts/make_smoke_data.py
ml/.venv/bin/python ml/cli.py train --variant real --data-root ml/artifacts/smoke-data \
  --artifact ml/artifacts/light.joblib --output ml/artifacts/smoke_train.json
ml/.venv/bin/python ml/check.py --engine light                               # "ready": true
ml/.venv/bin/python ml/cli.py single --text "В третьем подъезде не работает лифт"
ml/.venv/bin/python ml/cli.py chat --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl
ml/.venv/bin/python ml/cli.py eval --split test --data-root ml/artifacts/smoke-data \
  --output ml/artifacts/smoke_eval.json
```

Ожидаемо: лифт → `"is_problem":true,"fine_class":"elevator_out"`; «Соседи, во
сколько собрание?» → `"is_problem":false`; лента из трёх сообщений →
`created_preliminary`, `attached`, `resolution_pending_human` для `case-1`.
Отчёты `train`/`eval` пишите в `ml/artifacts/` (как выше): без `--output` команды
перезапишут отчёты исследований в `ml/experiments/`. Проверено 28.09.2026: Windows 11 и
чистый контейнер `python:3.12.11-slim-bookworm` (Linux), Python 3.12, scikit-learn 1.7.

**Начните с [пошагового руководства](docs/RUN_GUIDE.md):** там есть установка, запуск одного сообщения и чата, примеры ответов, проверка качества, запуск в чистом клоне и объяснение полей результата. Ниже — устройство, результаты опытов и ограничения. Имена режимов и полей ответа оставлены на английском, поскольку это точные названия команд и полей программы.

## Итоговая поставка: без LLM и API-ключей

Запускаемый из репозитория `ml/cli.py` использует **только локальные обученные модели и правила**. Все его режимы (`single`, `chat`, `replay`, `eval`, `train`) обходятся без языковой модели через API, не читают ключи и не отправляют сообщения в сеть. Усиленный вариант (`heavy`) берёт веса E5 и ruBERT из локальных файлов; отсутствие весов покажет `ml/check.py`. Для работы программы **не нужен ключ Polza.ai или другого провайдера**. Прямые расходы на запросы к API — **0 ₽**. Установка библиотек и первоначальная загрузка открытых весов на новой машине могут требовать интернет, но не платный ключ.

Программы небольшого платного исследования лежат отдельно в `ml/experiments/06_llm_cascade/` и не подключаются при обычном запуске. Их дополнительная библиотека вынесена в `ml/requirements-llm-pilot.txt`. Файл с исследовательским ключом в `ml/artifacts/` исключён из Git. Веса моделей тоже не включены в Git из-за размера: в чистом клоне их надо подготовить по руководству, **без платного API-ключа**.

В небольшом исследовании на 10 заранее выбранных трудных **синтетических** сообщениях локальная модель совпала с меткой в 2 случаях, Qwen — в 4, gpt-oss-120b — в 5. Это другая выборка, поэтому её нельзя сопоставлять с итоговой проверкой на реальных чатах и выдавать за качество поставляемой программы. Улучшение на независимом реальном потоке не доказано; объединение сообщений языковой моделью также не подтверждено. При будущей интеграции можно снова проверить выборочное использование языковой модели на трудных случаях, храня ключ только на сервере. Нынешний модуль полностью работает без неё.

**Итог на отложенной проверочной части данных:** усиленный вариант находит проблемы с показателем AP **0,900 / 0,829** и получает среднюю по классам оценку F1 **0,669 / 0,571** для WhatsApp / Telegram. При объединении сообщений об одной проблеме F1 равна **0,354**, а доля верных объединений среди предложенных — **0,928** на отдельно размеченных ассистентом чатах. Это предварительная оценка: независимой человеческой разметки нет. Проверка срочности пропустила почти половину экстренных случаев (полнота 0,507), поэтому на неё нельзя полагаться для самостоятельной тревоги.

**Как читать показатели:** AP оценивает, насколько хорошо модель расставляет сообщения о проблемах выше остальных при разных порогах; чем ближе к 1, тем лучше. *Точность* — доля верных среди предложенных проблем или связей; *полнота* — доля найденных среди всех имеющихся. F1 объединяет точность и полноту. «Средняя по классам F1» даёт каждому наблюдаемому классу равный вес, включая редкие классы и «нет проблемы». `train` — обучение, `val` — часть для выбора настроек, `test` — отложенная проверка. Эти названия сохранены в командах и путях к файлам.

**Что дали дополнительные опыты:** поиск похожих сообщений по словам (BM25) и новая общая модель с несколькими выходами оказались хуже выбранного сочетания моделей. Дополнительный определитель «проблема / не проблема» на ruBERT повысил оценку F1 на уже использованной части для выбора настроек с 0,697 до 0,723, но не повысил средний F1 на ранее просмотренной проверочной части: он остался 0,620. Поэтому рабочий вариант не меняли по этому результату. Подробная методика — в [третьем раунде исследований](docs/RESEARCH_ROUND3.md), платный опыт — в [отдельном плане](docs/LLM_CASCADE_PLAN.md).

| Дополнительная проверка | Результат | Вывод |
|---|---:|---|
| 67 сочетаний весов двух определителей класса на повторно использованной `val` | лучший F1 0,705 против 0,697; интервал неопределённости разницы включает ноль | Сохранить равные доли 50/50 |
| Поиск похожих сообщений BM25 вместе с BERT на `val` | F1 0,664 против 0,697 | Не заменять словесные и буквенные признаки TF-IDF |

| Новый определитель наличия проблемы на ранее просмотренном `test` | F1 0,620 против 0,620; AP вырос в обоих чатах | Не менять рабочий порог по повторной проверке |
| Обученная модель связи двух сообщений, 2 ранее просмотренных дня | F1 групп 0,552/0,694, но доля верных объединений 0,398/0,548 | Слишком много ошибочных объединений |

## Запуск и проверка

Команды выполняются из корня репозитория. Веса обученных моделей и набор v3.0 есть только у автора модуля; в чистом клоне их нет — модуль целиком проверяется [смоук-запуском на синтетике](#запуск-в-чистом-клоне-без-закрытых-данных). Нужен Python 3.10 или новее. Подробные действия для обоих случаев, пояснение ошибок и примеры — в [руководстве по запуску](docs/RUN_GUIDE.md).

```powershell
python -m pip install -r ml/requirements-embeddings.txt
python ml/check.py --engine heavy --data-root <путь к набору v3.0>
```

**Рекомендуемый вариант с лучшей измеренной классификацией:**

```powershell
python ml/cli.py single --engine heavy --text "В подъезде нет горячей воды"
python ml/cli.py chat --engine heavy --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl
python ml/cli.py eval --engine heavy --split test --data-root <путь к набору v3.0> --output ml/artifacts/my_eval.json
```

Вымышленный пример чата создаёт предварительную заявку `case-1`, прикрепляет к ней второе сообщение и оставляет открытой после фразы «воду дали». Файл чата содержит по одному сообщению на строку; программа выдаёт по одному решению на строку. В руководстве показаны содержимое файла и смысл действий `created_preliminary`, `attached`, `resolution_pending_human`. Оценка качества (`eval`) выводит общие числа без исходных сообщений.

Если видеокарты или усиленных весов нет, используйте **облегчённый вариант для процессора**. Установите `ml/requirements.txt`, выполните `python ml/check.py --engine light`, затем замените `heavy` на `light` в командах выше. Если в чистом клоне отсутствует и лёгкий файл `light.joblib`, его можно создать из набора v3.0 командой обучения из [руководства](docs/RUN_GUIDE.md#если-усиленные-веса-отсутствуют). В этой рабочей копии повторное обучение не требуется.

В ответе на одно сообщение есть наличие проблемы, её вид, категория для приложения, подсказка адресата, срочность и упомянутый подъезд/этаж. [Таблица полей](docs/RUN_GUIDE.md#как-читать-результат) переводит английские названия на обычный язык. `requires_human_confirmation` — информационная пометка, она **не останавливает** программу. Без дополнительной проверки не отправляйте и не закрывайте реальные заявки автоматически: адресат приблизителен, а модель срочности пропускает часть событий.

## Как устроена система

1. **Есть ли проблема.** Сначала отдельный определитель отсеивает обычную беседу. Облегчённый вариант ищет характерные сочетания букв и слов с помощью TF-IDF и логистической регрессии. Усиленный добавляет смысловое представление текста от E5. Они обучены на реальных обучающих сообщениях и на 735 допустимых для этой задачи искусственных примерах. Порог настроен на отдельной реальной части данных для точности около 0,80.
2. **Какого вида проблема.** Если первый этап нашёл проблему, второй выбирает один из 33 подробных классов. В усиленном варианте две модели класса голосуют поровну: дообученный ruBERT и лёгкая модель на сочетаниях букв и слов. Их ошибки частично различаются, поэтому совместное решение лучше. Отдельная таблица `configs/class_mapping.yaml` переводит класс в категории приложения и подсказку адресата; она не знает реального исполнителя конкретного дома.
3. **Срочность и смысл реплики.** Ещё две отдельные модели определяют возможную экстренность и является ли фраза жалобой, вопросом, объявлением или сообщением об устранении. Прямые слова о риске дают дополнительный признак срочного просмотра. Эти сигналы не создают настоящую заявку сами по себе.
4. **Объединение сообщений.** Программа сопоставляет только сообщения одного дома. Она учитывает класс, подъезд, вид лифта, время, ответ на предыдущую реплику и общие слова. По стандартному правилу объединение осторожное; явный параметр `service_context_6h` позволяет объединять сообщения об общедомовом отключении воды, отопления или света из разных подъездов в течение шести часов. Объявление о плановом отключении не открывает заявку. Сообщение об устранении общедомовой проблемы само не закрывает её.

Названия TF-IDF, E5 и ruBERT обозначают конкретные проверенные методы и модели, поэтому оставлены как имена собственные. Разбор нынешнего приложения — в [описании решения](docs/CURRENT_SOLUTION.md); различия списков классов — в [таблице соответствия](docs/CLASS_MAPPING.md). Нынешнее приложение смотрит на окно сообщений, а обучающий набор помечает отдельные сообщения. Поэтому приведённые ниже оценки относятся к самостоятельному модулю; напрямую сравнивать их с точностью нынешнего приложения нельзя.

## Почему выбран этот вариант

На отложенных сообщениях усиленная система лучше облегчённой: разница AP определения проблемы +0,037/+0,051, средней F1 всей классификации +0,049/+0,058 для WhatsApp/Telegram. Есть и практические причины выбора:

| Решение | Дополнительное основание |
|---|---|
| Отдельные этапы «есть ли проблема» и «какого она вида» | Проблемами являются только 9–12% сообщений. Отдельный первый этап позволяет ограничивать ложные заявки. Общая модель на все классы чаще путается из-за многочисленных обычных сообщений. |
| E5 вместе с буквенными и словесными признаками для первого этапа | E5 учитывает смысл переформулировок, буквенные признаки помогают при коротких фразах и опечатках. Оба работают на этой машине. |
| ruBERT и лёгкий определитель класса поровну | Модели исправляют разные ошибки, в том числе у редких классов. Другие доли смешивания на уже использованной настроечной части не дали устойчивого выигрыша. |
| Правило `service_context_6h` для демонстрации чата | Учитывает дом, время, подъезд, ответ на реплику и общедомовые услуги. Оно нашло больше правильных связей; обученная модель пар слишком часто объединяла разные события. Более осторожный вариант называется `conservative`. |
| Полностью местная обработка | Нет цены за запрос, сетевой задержки и зависимости от внешнего сервиса. Малое исследование языковых моделей не доказало улучшения на реальном потоке. |

При обработке усиленный вариант занял около 2,3 ГБ оперативной и 1,8 ГБ видеопамяти на проверенной GTX 1650; половина одиночных запросов после загрузки уложилась в 33,5 мс. Облегчённый занял около 247 МБ оперативной памяти и уложился в 8,1 мс. При нехватке памяти доступен облегчённый вариант; для лучшего измеренного качества на этой машине рекомендуется `heavy`. Оба работают без оператора в консоли, но не подтверждают фактический адресат, срочность или устранение проблемы.

## Данные и проверка

Для обучения использованы **обезличенные сообщения из двух домовых чатов одного дома — WhatsApp и Telegram**, набор v3.0. Перед передачей текстов разметчику номера телефонов, квартиры, имена, ссылки и другие личные признаки заменили условными обозначениями, а авторов — псевдонимами. Это делалось для снижения риска раскрытия личной информации. Автоматическое обезличивание **не гарантирует полного удаления** всех сведений: паспорт набора отмечает остаточные случаи. Подробности — в `docs/ai/ML_CONTEXT.md`, §5 и §10, и `datasets/README.md`, §7 (эти файлы находятся в исходной папке проекта, вне этой ветки).

Разметку подготовил агент на **Claude Opus 5.5** по формальным правилам: для WhatsApp было два полных независимых прохода; для Telegram второй проход охватил трудные сообщения, а часть простых получила один уверенный голос. Спорные сообщения исключали. Люди эти метки не проверяли. Название «Opus 5.5» взято из паспорта v3.0; это точное обозначение вместо сокращённого «Opus 5». Отдельно были созданы искусственные примеры для обучения; на проверочной части их нет.

Объём принятого реального набора: WhatsApp — 3 536 обучающих, 1 008 настроечных, 1 765 проверочных сообщений; Telegram — 13 397, 3 195 и 6 147 соответственно. Для срочности есть отдельный набор. Настройки и пороги подбирались на `val`, итоговые числа считались на `test`. Связанные сообщения и точные повторы разделены исходным разбиением. Диапазоны неопределённости оценены повторной выборкой целых групп сообщений; они не равны доказательству качества на другом доме.

Для объединения сообщений создана отдельная разметка ассистента на 205 сообщениях трёх дней, но независимого человеческого эталона по-прежнему нет. Исключение спорных записей может завышать оценки качества живого чата. Исходные переписки и веса моделей не добавлены в Git; веса остаются локальными и могут содержать сведения об обучении.

### Проверка на лентах чата

Программа `experiments/04_grouping/replay_real.py` восстановила порядок сообщений за три заранее выбранных дня из обезличенных файлов. Дни могли содержать тексты прежнего обучения и проверок, поэтому это **проверка поведения на потоке**, а не независимая оценка качества. На спокойном дне из 268 сообщений усиленная система не создала предварительных заявок. На двух днях с проблемами она создала 39 заявок из 182 сообщений и 27 из 138 при осторожном объединении. По принятой исходной разметке первый этап нашёл 35 из 45 и 35 из 38 проблем. Среди ранее исключённых спорных сообщений он предложил 12 из 26 и 15 из 35 как возможные проблемы; правильность этих предложений неизвестна.

Широкое правило «тот же вид проблемы в пределах 6–24 часов» сократило число заявок до 15 и 11, но ошибочно собрало сообщения **разных видов** в 1 и 2 группах. На слабом наборе пар оно выглядит идеальным только из-за способа создания меток. Для более полной группировки следует явно указать `service_context_6h`; по умолчанию действует осторожное `conservative`. Точность на новых днях неизвестна. Числа без текстов — в `experiments/04_grouping/replay_real_heavy.json`.

Добавление соседних реплик не помогло первому этапу: на настроечной части Telegram AP упал с 0,862 до 0,836 при добавлении текста сообщения, на которое отвечают, и до 0,609 при добавлении двух предыдущих сообщений. Исходная разметка относится к отдельной реплике; связь `reply_to` оставлена для объединения сообщений.

## Ошибки и ограничения

- У облегчённого варианта на проверочной части особенно слабы редкие классы: «мусор не вывезен», «вредители», «порча лифта», «нет холодной воды» и «другая проблема». Например, для невывезенного мусора F1 равна нулю, но есть всего 3 случая в WhatsApp и 1 в Telegram; такие числа нестабильны. Подробный отчёт по каждому классу — в `experiments/eval_best_test.json`; слабые классы усиленного варианта перечислены выше.
- На **вымышленном** тексте «Во втором подъезде не работает грузовой лифт» облегчённый вариант верно выбирает поломку лифта, но ошибочно ставит `emergency=true`. Усиленный вариант на фразе «В подъезде не работает лифт» тоже ошибочно отметил срочность. Фраза «Запах газа в подъезде, срочно!» получает правильный вид проблемы, но облегчённая модель не ставит `emergency=true`; отдельное словесное правило поднимает признак срочного просмотра. Эти примеры проверены командой `single`, но не добавлены к общим оценкам качества.
- Короткие ответы, отрицания, плановые отключения и фразы «починили» требуют понимания соседних сообщений. Исходная метка дана отдельной реплике, поэтому на ней нельзя честно оценить выгоду от просмотра всего разговора. Связь `reply_to` используется при объединении и обработке сообщения об устранении. Автоматическое закрытие остаётся ненадёжным.
- Классы L3 не кодируют территорию, регион и исполнителя. Даже «точное» отображение подтипа не доказывает адресата. Шесть классов нарушений соседей/парковки/безопасности не создают обычную заявку УК по умолчанию. Без внешних данных об адресе и зоне ответственности адресат остаётся подсказкой.
- Данные двух чатов одного дома и синтетика не доказывают перенос на другой дом или MAX. Разметка не проверена человеком; спорные случаи исключены. Реальные потоки и личные данные нельзя публиковать.

## Как модуль войдёт в приложение

При дальнейшей разработке для него добавят подключение к основному процессу обработки чата и **выбор способа анализа**: нынешний способ приложения или этот местный ML-модуль. Сначала оба способа следует сравнить на одинаковых обезличенных сообщениях без отправки внешних заявок; затем выбрать режим в настройках приложения. Сейчас переключателя нет: консольный модуль живёт отдельно. При выборе нынешнего способа его существующая зависимость от внешнего API останется; **ML-режим не требует API-ключа**.

В будущем сообщения для обучения будут обезличиваться и сохраняться в базе вместе с версией модели и её исходным решением. Оператор сможет подтвердить ответ, опровергнуть его или указать правильный класс и связь с заявкой. Непроверенные сообщения при необходимости смогут дополнительно размечать люди или модель, но источник метки должен быть записан: автоматически полученную метку нельзя считать подтверждением оператора. Из-за затрат модели будут дообучаться **периодически**, когда накопятся новые данные, а не после каждого исправления. Подробный порядок — в [плане внедрения](docs/FUTURE_INTEGRATION.md).

Между обучениями можно показывать старшему администратору статистику **по каждому виду проблемы**. Предложенный множитель:

```text
W = 1 + α × (1 − exp(−N/τ)) × (C/N − θ), если N > 0; при N = 0 берём W = 1.
```

Здесь `N` — сколько предсказаний **этого класса** проверили операторы, `C` — сколько из них признали верными. `α` задаёт силу влияния, `τ` — сколько проверок нужно для заметного влияния, `θ` — желаемую долю верных ответов. Эти три параметра сможет настраивать старший администратор. В предложенном варианте значения равны `α=1`, `τ=100000`, `θ=1`: при малом числе проверок почти ничего не меняется, а при ошибках коэффициент только **уменьшает** оценку класса. Формула показывает избыток ошибочных предложений, но **не видит пропущенные случаи**, когда модель не предложила нужный класс. Для них понадобится отдельная проверка части отклонённых сообщений. Пока надёжнее показывать `W` как показатель перекоса и повод собрать примеры для следующего обучения. Менять им оценки классов стоит лишь после проверки на новых данных; сейчас формула **не действует в программе**. Условия применения, пример расчёта и ограничения — в [плане внедрения](docs/FUTURE_INTEGRATION.md#формула-поправки-из-предложенного-макета).
