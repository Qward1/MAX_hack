# ДомСигнал: самостоятельный модуль анализа сообщений

Модуль читает сообщения домового чата, определяет, есть ли проблема, предлагает её вид и адресата, оценивает срочность и объединяет сообщения об одной проблеме в предварительную заявку. Он работает из консоли **отдельно от основного приложения**, офлайн и без API-ключей. Рекомендуемый вариант сочетает три локальные модели; для обычного процессора есть облегчённый вариант. Это самостоятельный модуль: в Docker-образ продукта он не входит; план подключения — [docs/FINAL_PLAN.md](../docs/FINAL_PLAN.md).

## Запуск в чистом клоне без закрытых данных

Набора v3.0 и обученных весов в репозитории нет. Чтобы проверить, что код модуля
работает целиком — обучение, одно сообщение, лента чата, оценка, — используйте
синтетический смоук-набор: его строит `ml/scripts/make_smoke_data.py` из шаблонов
(ни одного реального сообщения) в игнорируемую Git папку `ml/artifacts/smoke-data/`.
Обученная на нём модель знает 10 классов и нужна только для проверки
работоспособности; её числа **не являются оценкой качества**.

```bash
python -m venv ml/.venv            # Windows: ml\.venv\Scripts\python вместо ml/.venv/bin/python
ml/.venv/bin/python -m pip install -r ml/requirements.txt
PYTHONPATH=ml/src ml/.venv/bin/python -m unittest discover -s ml/tests      # тесты объединения и слотов
ml/.venv/bin/python ml/scripts/make_smoke_data.py
ml/.venv/bin/python ml/cli.py train --variant real --data-root ml/artifacts/smoke-data \
  --artifact ml/artifacts/light.joblib --output ml/artifacts/smoke_train.json
ml/.venv/bin/python ml/check.py --engine light                               # "ready": true
ml/.venv/bin/python ml/cli.py single --text "В третьем подъезде не работает лифт"
ml/.venv/bin/python ml/cli.py chat --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl
ml/.venv/bin/python ml/cli.py eval --split test --data-root ml/artifacts/smoke-data \
  --output ml/artifacts/smoke_eval.json
```

Ожидаемо: лифт → `"is_problem":true,"fine_class":"elevator_out"`; «Соседи, во
сколько собрание?» → `"is_problem":false`; лента из трёх сообщений →
`created_preliminary`, `attached`, `resolution_pending_human` для `case-1`.
Отчёты `train`/`eval` пишите в `ml/artifacts/` (как выше): без `--output` команды
перезапишут отчёты исследований в `ml/experiments/`. Проверено 28.09.2026: Windows 11 и
чистый контейнер `python:3.12.11-slim-bookworm` (Linux), Python 3.12, scikit-learn 1.7.

**Начните с [пошагового руководства](docs/RUN_GUIDE.md):** там есть установка, запуск одного сообщения и чата, примеры ответов, проверка качества, запуск в чистом клоне и объяснение полей результата. Ниже — устройство, опыты и ограничения. Имена режимов и полей ответа оставлены на английском, поскольку это точные названия команд и полей программы.

## Итоговая поставка: без LLM и API-ключей

Запускаемый из репозитория `ml/cli.py` использует **только локальные обученные модели и правила**. Все его режимы (`single`, `chat`, `replay`, `eval`, `train`) обходятся без языковой модели через API, не читают ключи и не отправляют сообщения в сеть. Усиленный вариант (`heavy`) берёт веса E5 и ruBERT из локальных файлов; отсутствие весов покажет `ml/check.py`. Для работы программы **не нужен ключ внешнего провайдера**. Прямые расходы на запросы к API — **0 ₽**. Установка библиотек и первоначальная загрузка открытых весов на новой машине могут требовать интернет, но не платный ключ.

Программы небольшого исследования с внешними языковыми моделями лежат отдельно в `ml/experiments/06_llm_cascade/` и не подключаются при обычном запуске. Их дополнительная библиотека вынесена в `ml/requirements-llm-pilot.txt`; файл с исследовательским ключом в `ml/artifacts/` исключён из Git. Исследование было небольшим и основания включать внешнюю модель в модуль не дало ([план и выводы](docs/LLM_CASCADE_PLAN.md)); модуль полностью работает без неё. Веса моделей не включены в Git из-за размера: в чистом клоне их надо подготовить по руководству, **без платного API-ключа**.

## Запуск и проверка

Команды выполняются из корня репозитория. Веса обученных моделей и набор v3.0 есть только у автора модуля; в чистом клоне их нет — модуль целиком проверяется [смоук-запуском на синтетических данных](#запуск-в-чистом-клоне-без-закрытых-данных). Нужен Python 3.10 или новее. Подробные действия для обоих случаев, пояснение ошибок и примеры — в [руководстве по запуску](docs/RUN_GUIDE.md).

```powershell
python -m pip install -r ml/requirements-embeddings.txt
python ml/check.py --engine heavy --data-root <путь к набору v3.0>
```

**Рекомендуемый (усиленный) вариант:**

```powershell
python ml/cli.py single --engine heavy --text "В подъезде нет горячей воды"
python ml/cli.py chat --engine heavy --merge-policy service_context_6h --file ml/examples/demo_chat.jsonl
python ml/cli.py eval --engine heavy --split test --data-root <путь к набору v3.0> --output ml/artifacts/my_eval.json
```

Вымышленный пример чата создаёт предварительную заявку `case-1`, прикрепляет к ней второе сообщение и оставляет открытой после фразы «воду дали». Файл чата содержит по одному сообщению на строку; программа выдаёт по одному решению на строку. В руководстве показаны содержимое файла и смысл действий `created_preliminary`, `attached`, `resolution_pending_human`. Оценка качества (`eval`) выводит общие числа без исходных сообщений.

Если видеокарты или усиленных весов нет, используйте **облегчённый вариант для процессора**. Установите `ml/requirements.txt`, выполните `python ml/check.py --engine light`, затем замените `heavy` на `light` в командах выше. Если в чистом клоне отсутствует и облегчённый файл `light.joblib`, его можно создать из набора v3.0 командой обучения из [руководства](docs/RUN_GUIDE.md#если-усиленные-веса-отсутствуют).

В ответе на одно сообщение есть наличие проблемы, её вид, категория для приложения, подсказка адресата, срочность и упомянутый подъезд/этаж. [Таблица полей](docs/RUN_GUIDE.md#как-читать-результат) переводит английские названия на обычный язык. `requires_human_confirmation` — информационная пометка, она **не останавливает** программу. Ответ модуля предварительный: адресат — подсказка, а заявки отправляет и закрывает человек.

## Как устроена система

1. **Есть ли проблема.** Сначала отдельный определитель отсеивает обычную беседу. Облегчённый вариант ищет характерные сочетания букв и слов с помощью TF-IDF и логистической регрессии. Усиленный добавляет смысловое представление текста от E5. Они обучены на реальных обучающих сообщениях и на 735 допустимых для этой задачи искусственных примерах. Порог настроен на отдельной реальной части данных для точности около 0,80.
2. **Какого вида проблема.** Если первый этап нашёл проблему, второй выбирает один из 33 подробных классов. В усиленном варианте две модели класса голосуют поровну: дообученный ruBERT и облегчённая модель на сочетаниях букв и слов. Их ошибки частично различаются, поэтому совместное решение лучше. Отдельная таблица `configs/class_mapping.yaml` переводит класс в категории приложения и подсказку адресата; она не знает реального исполнителя конкретного дома.
3. **Срочность и смысл реплики.** Ещё две отдельные модели определяют возможную экстренность и является ли фраза жалобой, вопросом, объявлением или сообщением об устранении. Прямые слова о риске дают дополнительный признак срочного просмотра. Эти сигналы не создают настоящую заявку сами по себе.
4. **Объединение сообщений.** Программа сопоставляет только сообщения одного дома. Она учитывает класс, подъезд, вид лифта, время, ответ на предыдущую реплику и общие слова. По стандартному правилу объединение осторожное; явный параметр `service_context_6h` позволяет объединять сообщения об общедомовом отключении воды, отопления или света из разных подъездов в течение шести часов. Объявление о плановом отключении не открывает заявку. Сообщение об устранении общедомовой проблемы само не закрывает её.

Названия TF-IDF, E5 и ruBERT обозначают конкретные проверенные методы и модели, поэтому оставлены как имена собственные. Разбор нынешнего приложения — в [описании решения](docs/CURRENT_SOLUTION.md); различия списков классов — в [таблице соответствия](docs/CLASS_MAPPING.md). Нынешнее приложение смотрит на окно сообщений, а обучающий набор помечает отдельные сообщения. Поэтому оценки модуля в отчётах опытов напрямую сравнивать с точностью нынешнего приложения нельзя.

## Почему выбран этот вариант

Усиленная система выбрана по сравнению с облегчённой на отложенной части набора v3.0 (отчёты — `experiments/eval_best_test.json` и `experiments/eval_hybrid_e5_rubert_sparse_ensemble_test.json`). Есть и практические причины выбора:

| Решение | Дополнительное основание |
|---|---|
| Отдельные этапы «есть ли проблема» и «какого она вида» | По разметке набора проблемы составляют 9–12% сообщений. Отдельный первый этап позволяет ограничивать ложные заявки. Общая модель на все классы чаще путается из-за многочисленных обычных сообщений. |
| E5 вместе с буквенными и словесными признаками для первого этапа | E5 учитывает смысл переформулировок, буквенные признаки помогают при коротких фразах и опечатках. Оба работают на машине с GTX 1650 4 ГБ. |
| ruBERT и облегчённый определитель класса поровну | Модели исправляют разные ошибки, в том числе у редких классов. Другие доли смешивания не дали устойчивого выигрыша. |
| Правило `service_context_6h` для демонстрации чата | Учитывает дом, время, подъезд, ответ на реплику и общедомовые услуги. Оно нашло больше правильных связей; обученная модель пар слишком часто объединяла разные события. Более осторожный вариант называется `conservative`. |
| Полностью местная обработка | Нет цены за запрос, сетевой задержки и зависимости от внешнего сервиса. |

При обработке усиленный вариант занял около 2,3 ГБ оперативной и 1,8 ГБ видеопамяти на GTX 1650; половина одиночных запросов после загрузки уложилась в 33,5 мс. Облегчённый занял около 247 МБ оперативной памяти и уложился в 8,1 мс. При нехватке памяти доступен облегчённый вариант; при наличии видеокарты рекомендуется `heavy`. Оба работают без оператора в консоли, но не подтверждают фактический адресат, срочность или устранение проблемы.

## Данные

Для обучения использованы **обезличенные сообщения из двух домовых чатов одного дома — WhatsApp и Telegram**, набор v3.0. Перед разметкой номера телефонов, квартиры, имена, ссылки и другие личные признаки заменили условными обозначениями, а авторов — псевдонимами. Автоматическое обезличивание **не гарантирует полного удаления** всех сведений, поэтому набор не публикуется; его паспорт хранится вместе с набором вне репозитория.

Разметка выполнена по формальным правилам; спорные сообщения исключены. Отдельно созданы искусственные примеры для обучения; в проверочной части их нет.

Объём принятого реального набора: WhatsApp — 3 536 обучающих, 1 008 настроечных, 1 765 проверочных сообщений; Telegram — 13 397, 3 195 и 6 147 соответственно. Для срочности есть отдельный набор. Настройки и пороги подбирались на `val`, итоговые числа считались на `test`. Связанные сообщения и точные повторы разделены исходным разбиением. Диапазоны неопределённости в отчётах оценены повторной выборкой целых групп сообщений.

Для проверки объединения сообщений отдельно размечены три полных дня чата (205 сообщений) до просмотра результатов объединения; протокол — [`experiments/04_grouping/MANUAL_ANNOTATION.md`](experiments/04_grouping/MANUAL_ANNOTATION.md), методика — [отчёт о чатах](docs/CHAT_INCIDENT_EVAL.md). Исходные переписки и веса моделей не добавлены в Git; веса остаются локальными и могут содержать сведения об обучении.

## Опыты и отчёты

Каждый опыт сохраняет числовой отчёт без текстов сообщений в `ml/experiments/`. `train` — обучение, `val` — часть для выбора настроек, `test` — отложенная проверка. AP оценивает, насколько хорошо модель ставит сообщения о проблемах выше остальных при разных порогах; *точность* — доля верных среди предложенных проблем или связей; *полнота* — доля найденных среди всех имеющихся; F1 объединяет точность и полноту; «средняя по классам F1» (macro-F1) даёт каждому наблюдаемому классу равный вес.

### Воспроизведение усиленного варианта

Для повторения обучения за указанное время нужна видеокарта GTX 1650 с 4 ГБ памяти или более мощная. Открытые исходные веса скачиваются один раз; тексты домовых чатов при этом не отправляются. python -c "from huggingface_hub import snapshot_download; snapshot_download('ai-forever/ruBert-base', local_dir='ml/artifacts/models/rubert-base')"

Дообучение ruBERT заняло 1 353 с (22,6 мин), пик видеопамяти — 3 418 МБ, файл весов — 713 МБ. Преобразование обучающих, настроечных и искусственных сообщений в числовые признаки E5 заняло 87 с; обучение первого этапа с готовыми признаками — 10 с. Программа `train_encoder.py` создаёт места для четырёх выходов, но при показанных параметрах обучает и использует **только определитель вида проблемы**. Её служебные оценки остальных необученных выходов не являются результатом. Для наличия проблемы, смысла реплики и срочности применяются отдельные модели.

Облегчённая модель обучается примерно 14 с на указанном компьютере. ## Ограничения

- Короткие ответы, отрицания, плановые отключения и фразы «починили» требуют понимания соседних сообщений. Исходная метка дана отдельной реплике; связь `reply_to` используется при объединении и обработке сообщения об устранении. Закрытие заявки остаётся за человеком.
- Классы L3 не кодируют территорию, регион и исполнителя. Даже «точное» отображение подтипа не доказывает адресата. Шесть классов нарушений соседей/парковки/безопасности не создают обычную заявку УК по умолчанию. Без внешних данных об адресе и зоне ответственности адресат остаётся подсказкой.
- Модуль обучен на чатах одного дома; перенос на другие дома и на MAX требует отдельной проверки. Реальные потоки и личные данные не публикуются.

## Как модуль войдёт в приложение

При дальнейшей разработке для него добавят подключение к основному процессу обработки чата и **выбор способа анализа**: нынешний способ приложения или этот местный ML-модуль. Сначала оба способа следует сравнить на одинаковых обезличенных сообщениях без отправки внешних заявок; затем выбрать режим в настройках приложения. Консольный модуль сейчас живёт отдельно. При выборе нынешнего способа его существующая зависимость от внешнего API останется; **ML-режим не требует API-ключа**.

В будущем сообщения для обучения будут обезличиваться и сохраняться в базе вместе с версией модели и её исходным решением. Оператор сможет подтвердить ответ, опровергнуть его или указать правильный класс и связь с заявкой. Непроверенные сообщения при необходимости смогут дополнительно размечать люди или модель, но источник метки должен быть записан: автоматически полученную метку нельзя считать подтверждением оператора. Из-за затрат модели будут дообучаться **периодически**, когда накопятся новые данные, а не после каждого исправления. Подробный порядок — в [плане внедрения](docs/FUTURE_INTEGRATION.md).

Между обучениями можно показывать старшему администратору статистику **по каждому виду проблемы**. Предложенный множитель:

```text
W = 1 + α × (1 − exp(−N/τ)) × (C/N − θ), если N > 0; при N = 0 берём W = 1.
```

Здесь `N` — сколько предсказаний **этого класса** проверили операторы, `C` — сколько из них признали верными. `α` задаёт силу влияния, `τ` — сколько проверок нужно для заметного влияния, `θ` — желаемую долю верных ответов. Эти три параметра сможет настраивать старший администратор. В предложенном варианте значения равны `α=1`, `τ=100000`, `θ=1`: при малом числе проверок почти ничего не меняется, а при ошибках коэффициент только **уменьшает** оценку класса. Формула показывает избыток ошибочных предложений, но **не видит пропущенные случаи**, когда модель не предложила нужный класс. Для них понадобится отдельная проверка части отклонённых сообщений. Поэтому `W` сначала показывается как показатель перекоса и повод собрать примеры для следующего обучения; менять им оценки классов стоит лишь после проверки на новых данных. Условия применения, пример расчёта и ограничения — в [плане внедрения](docs/FUTURE_INTEGRATION.md#формула-поправки-из-предложенного-макета).
