# Раунд 3: конкуренты TF-IDF и узкий LLM-каскад

**Коротко для читателя:** проверены другой способ поиска похожих сообщений (BM25), разные доли двух определителей вида проблемы, общая модель с несколькими выходами, новый определитель наличия проблемы, обученная связь двух сообщений и небольшое исследование с внешними языковыми моделями. Ни один новый вариант не дал достаточно надёжного преимущества, чтобы заменить работающую местную систему. Исследование с внешними моделями не включено в запускаемый модуль. Объяснение без специальных терминов — в [главном описании модуля](../README.md); ниже сохранён технический протокол, числа — в файлах `experiments/`.

План зафиксирован 27.09.2026 **до новых запусков**. Код продукта не меняется. Выбор только на исходной реальной `val`, отдельно WhatsApp и Telegram; прежний `test` уже использовался для выбора предыдущей системы, поэтому повторные цифры на нём не будут называться независимой проверкой. Ручная разметка чатов содержит возможные пересечения с обучением классификатора и служит проверкой потока, а не новым классификационным test. В отчёты попадают только агрегаты без текстов.

## Диагноз

- Текущая система **уже двухуровневая**: гибридный gate `TF-IDF + E5` определяет наличие проблемы, затем условная голова ruBERT-base + разреженная голова определяет класс. Плоская модель на 34 класса и многоголовый `rubert-tiny2` проиграли на `val`; это не закрывает вопрос о более сильном gate-энкодере.
- Доля разреженной головы 0,5 была выбрана из грубой сетки `0, 0.1, 0.2, 0.3, 0.5, 0.7, 1`. Вклад TF-IDF нельзя оценить по названию модели: нужна абляция с нулевой долей и более плотной сеткой, одинаковым gate и одинаковой метрикой.
- BM25 — функция поиска похожих документов. Чтобы сравнить его с классификатором, используем BM25-kNN: поиск соседей только в **train**, голосование их классов и отдельную оценку gate. На коротких репликах word BM25 может уступить символьным n-граммам; это проверяемая гипотеза.
- Связи между сообщениями пока слабее самой классификации. LLM-кандидат должен решать **только** неуверенное решение или выбор связи среди нескольких уже открытых заявок, а не читать и переписывать весь поток.

## Исследовательские опоры

Выборочная передача сомнительных решений человеку или более сильной модели соответствует постановке selective classification: качество нужно смотреть вместе с долей покрытых сообщений, а не только с одной F1 ([Geifman, El-Yaniv, NeurIPS 2017](https://papers.nips.cc/paper_files/paper/2017/hash/4a8423d5e91fda00bb7e46540e2b0cf1-Abstract.html)). Для связи сообщений полезен двухшаговый подход: быстрый поиск небольшого числа кандидатов, затем парная модель, рассматривающая два текста совместно ([Sentence Transformers Cross-Encoder](https://www.sbert.net/examples/cross_encoder/applications/README.html)). Исследования disentanglement показывают необходимость размеченных структур ответов и глобального объединения, а не одной косинусной близости ([Jiang et al., NAACL 2018](https://aclanthology.org/N18-1164/), [Kummerfeld et al., ACL 2019](https://arxiv.org/abs/1810.11118)). Эти публикации обосновывают гипотезы, но не переносят свои метрики на домовые чаты.

|---|---|---|---|

| R3-B | Поиск BM25 может заменить разреженный классификатор | Word BM25-kNN на `train` с k=1,3,5,11; сравнить с TF-IDF-kNN, текущей разреженной головой и BERT при одинаковом gate | Если хуже BERT и не улучшает ансамбль, не включать; отдельно показать время/память |
| R3-C | Двухуровневый gate можно сделать без TF-IDF | Дообучить ruBERT-base на бинарной границе или общий multihead, сравнить AP, рабочие P/R и F1 полной цепочки с тем же классом | Замена только при улучшении AP/полной F1 и приемлемой цене инференса |
| R3-D | Разные головы делают разные ошибки | Пробовать голосование/смесь BERT, TF-IDF и BM25 только после отдельных измерений; анализировать дополнение ошибок, не число моделей | Отбрасывать добавку без прироста на `val` |
| R3-E | Каскад LLM может закрыть часть оставшихся ошибок дешёво | До 100 заранее выбранных трудных/контекстных окон; модели через маршруты провайдеров с хранением данных в РФ; сравнить с ML, долю маршрутизации, цену и F1 связей | Включать только на типах ошибок с измеренным выигрышем; внешние ответы не считаются золотой разметкой |

Реальные наборы имеют только 9–12% проблем и 33 редких проблемных класса. В каждой таблице считать полный macro-F1 по наблюдаемым классам каждого источника, gate AP, точность/полноту при выбранном на `val` пороге. Не оптимизировать отдельно по `test`. Для редких классов сообщать support. Для важного сравнения использовать групповой бутстрэп по `family_id`/`thread_id`, но не выдавать узкий интервал за доказательство на новом доме.

## LLM: стоимость и границы

Для каждого кандидата выбирался конкретный маршрут провайдера с хранением данных в РФ; цена такого маршрута заметно выше цены по умолчанию в карточке модели, которая может относиться к зарубежному маршруту. В реальном API-вызове провайдер закреплялся явно, резервный маршрут отключался. Бюджет пробного сравнения зафиксирован до запуска: не более 10 ₽ суммарно и 100 запросов на модель.

Исходные данные обезличены неидеально, поэтому перед API-вызовом нужны дополнительное удаление идентификаторов, минимальный контекст, ограничение объёма, отсутствие текстов в логах и явная проверка, что выбранный маршрут обрабатывает данные в РФ. Ключ хранится локально в игнорируемом Git файле; скрипт считывает его и не печатает.

## Результаты локальных проверок 27.09

- **Доля смешивания ruBERT/разреженной головы.** Лучший из 67 вариантов дал небольшой прирост на `val`, но интервалы разницы при групповом бутстрэпе пересекают ноль для обоих источников. Смесь 50/50 сохранена. `experiments/02_classes/round3_ensemble_val.json`.
- **Ошибки голов дополняют друг друга.** Каждая голова верна на части примеров, где ошибается другая, и смесь 50/50 сохраняет большую часть этих решений; польза разреженной головы распределена по разным классам. Убрать TF-IDF-голову без замены значит потерять часть правильных редких классов.
- **BM25.** BM25 word kNN и BM25-взвешенная линейная модель проиграли текущему классовому ансамблю. BM25 можно оставить для поиска кандидатов, но не как замену обученной головы. `experiments/02_classes/round3_bm25_val.json`.
- **Первый этап на векторах ruBERT.** Линейная бинарная голова на замороженных векторах дообученного ruBERT-base в смеси с текущим гейтом подняла AP и F1 цепочки на `val`; конфигурация и порог выбраны на той же `val`, поэтому это исследовательский сигнал. `experiments/01_gate/round3_frozen_rubert_gate_val.json`, проверка стабильности порога по 5 групповым фолдам — `experiments/01_gate/round3_group_cv_val.json`.
- **Рабочий порог.** Из целевых точностей гейта 0,70/0,80/0,90 выбранная ранее 0,80 даёт лучший F1 и сохраняет управляемую нагрузку оператора. `experiments/01_gate/round3_threshold_tradeoff.json`.
- **Выборочная маршрутизация.** Отбор по близости к порогу гейта и по малому отрыву двух классов действительно концентрирует ошибки; это **потолок возможности отбора**, а не оценка LLM. Для объединения полезнее проверять **решение о связи** среди открытых заявок вместе с наличием проблемы; одной поправки класса недостаточно.

## Поздние проверки: модель класса, gate и склейка

- Дообучена полная многоголовая `ruBERT-base` с головами класса, gate, utterance и safety: две эпохи, 9 121 обучающая запись после выборки отрицательных 3:1, GTX 1650, 2 293 с, пик GPU 3 418 МБ, checkpoint 713 МБ. Она уступила выбранному каскаду на `val`; встроенная бинарная голова не обошла отдельный гибридный gate по AP. `experiments/02_classes/encoder_base_multi_gate_r3_val.json`. Дальше увеличивать число эпох на этой же `val` без нового эталона не стали.
- Конфигурация нового gate, заранее выбранная на `val`, прогнана на **ранее уже просмотренном** `test` без подбора порога по нему. AP вырос, но средний полный macro-F1 не изменился: увеличение полноты сопровождалось снижением точности. Менять рабочую цепочку по этому эксперименту нельзя. `experiments/01_gate/round3_gate_reused_test.json`.
- Парная модель E5-косинус + время + слова + ответы + местоположение + предсказанные классы обучена на дне разработки и проверена на двух следующих днях. Обычное соединение выбранных рёбер транзитивно склеивало разные инциденты, а осторожный вариант с взаимными ближайшими соседями терял почти все связи. Заменить осторожное продуктовое правило она не может. `experiments/04_grouping/round3_pair_model.json`.
- Чтобы отделить нехватку gate от ошибок класса, на ранее просмотренном `test` посчитан диагностический оракул без обучения: идеальный gate при неизменной голове класса и идеальный класс при нынешнем gate. Это верхние границы отдельных исправлений с доступом к истинным меткам, а не прогноз следующей модели. `experiments/diagnostic_oracle_test.py`, `experiments/diagnostic_oracle_test.json`.

## Ограниченное исследование с внешними моделями

Вызовы выполнялись только с закреплённым маршрутом провайдера, для которого каталог показывал хранение данных в РФ; резервный маршрут отключён. Исходные тексты жителей, промпты, ответы и ключ не печатались и не коммитились. Использованы самостоятельно написанные и проверенные на личные сведения переформулировки, а также заранее выбранные трудные синтетические сообщения. Ни одна строка исследования не является эталонной разметкой.

- **Формат ответа.** У части моделей рассуждение расходует выходные токены: при малом лимите ответ не укладывается в JSON; увеличение лимита помогает, но не гарантирует короткий ответ. Это проверка подключения и формата, не точности.
- **Переформулировки.** Переформулирование убрало неуверенность локальной модели: заранее заданный узкий фильтр не направил бы эти сообщения во внешнюю модель, поэтому сравнение на них не измеряет полезность выборочного каскада. Изолированные пары связи не дают F1 итоговых заявок.
- **Трудные сообщения.** На небольшом заранее выбранном наборе трудных синтетических сообщений внешние модели исправили часть локальных ошибок. Это подтверждает, что отбор находит ошибки, но масштаб и прирост на реальном потоке неизвестны.

Все 114 вызовов исследования стоили 9,14 ₽ по возвращённому API `usage.cost_rub`, включая технические пробы и повтор формата. Это не оценка стоимости эксплуатации: среднее зависит от длины окна, модели, лимита рассуждений, маршрута и доли маршрутизации. Каскад с внешней моделью в `single/chat/eval` не включён; для продукта разумнее показывать локальный класс и возможную связь человеку. Скрипты исследования — `experiments/06_llm_cascade/`.
