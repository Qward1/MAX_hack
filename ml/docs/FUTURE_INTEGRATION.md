# План подключения к приложению и учёта исправлений

Этот документ описывает **будущее развитие**, а не возможности уже работающего консольного модуля. Сейчас модуль из `ml/` запускается отдельно, не читает базу приложения, не получает исправления операторов и не использует приведённую ниже формулу при классификации.

## Подключение к приложению

1. Сделать для локальной модели тот же вход и выход, которые ожидает существующий анализ сообщений: текст, идентификатор дома, время, связь с предыдущим сообщением; в ответе — наличие проблемы, класс, подсказка адресата, экстренность и связь с заявкой. Проверить соответствие классов по `ml/configs/class_mapping.yaml`.
2. Добавить в настройках приложения выбор способа анализа: **нынешний способ** или **локальная ML-модель**. Для сравнения сначала выполнять оба способа на обезличенных сообщениях без автоматического создания внешних заявок и показывать различия в статистике. После проверки можно разрешить выбор режима для конкретного дома или установки.
3. Оставить отправку и закрытие настоящих заявок за правилами приложения. Ответ локальной модели — предварительный: текущая проверка экстренности и объединения сообщений не позволяет считать каждое решение подтверждённым. Если нынешний способ использует внешний API, его ключ остаётся только на сервере; локальный ML-режим ключа не требует.

## Сбор данных и периодическое дообучение

В будущей версии приложения сообщения из чатов будут **обезличиваться до записи в учебную базу**. Вместе с текстом нужно сохранять время, дом в виде служебного идентификатора, версию модели, её решение и историю изменений метки. Доступ к базе, срок хранения и повторную проверку обезличивания следует настроить отдельно: исходный набор v3.0 показывает, что автоматическое удаление личных сведений бывает неполным. Сырые тексты не должны попадать в журналы работы модели.

Операторы смогут подтвердить решение, отклонить его или указать правильный класс и принадлежность к заявке. Исправление оператора хранится отдельно от исходного предсказания; иначе нельзя посчитать ошибки. Если операторы не успели проверить часть сообщений, для обучения допустима дополнительная разметка людьми или моделью с явной пометкой источника и степени уверенности. **Автоматическую доразметку нельзя считать проверкой человеком** или смешивать с ней при подсчёте приведённой ниже статистики.

Дообучение выполняется **периодически**, когда накопится достаточно новых подтверждённых примеров: каждый запуск требует вычислений и проверки качества. Новую модель нужно сравнить на более позднем периоде и, по возможности, на другом доме; фиксировать версию данных, показатели для каждого класса и ошибки объединения сообщений. Переход на новую версию и откат должны быть управляемыми. Между запусками можно собирать статистику по классам без переобучения.

## Формула поправки из предложенного макета

Для класса `c` берём **только проверенные оператором предсказания этого класса**:

$$
W_c=1+\alpha\left(1-e^{-N_c/\tau}\right)\left(\frac{C_c}{N_c}-\theta\right),\qquad N_c>0.
$$

Если `N_c=0`, полагаем `W_c=1`, потому что деление на ноль невозможно и данных для поправки нет.

| Величина | Простое объяснение |
|---|---|
| `N_c` | Сколько раз модель предложила класс `c` и оператор проверил именно это решение. |
| `C_c` | Сколько из этих `N_c` решений оператор признал правильными. Всегда `0 ≤ C_c ≤ N_c`. |
| `C_c/N_c` | Доля верных срабатываний среди проверенных предложений класса `c`, то есть точность срабатывания на проверенной части. |
| `α` | Максимальная сила поправки. `α=0` отключает её. Для этой схемы безопасный диапазон при настройке — `0 ≤ α ≤ 1`, чтобы множитель не стал отрицательным. |
| `τ` | Масштаб количества проверок: при `N_c=τ` статистика действует примерно на 63% полной силы. Чем больше `τ`, тем медленнее растёт влияние новых проверок. Требуется `τ>0`. |
| `θ` | Целевая доля верных срабатываний. При доле ниже `θ` множитель меньше 1, при доле выше — больше 1. Допустимый диапазон `0 ≤ θ ≤ 1`. |
| `W_c` | Показатель для класса `c`, который можно показать администратору; после отдельной проверки его можно попробовать как множитель для оценки класса. |

В предложенном варианте параметры равны `α=1`, `τ=100000`, `θ=1`. При таких настройках формула **никогда не повышает** оценку класса: `C_c/N_c ≤ 1`, значит `W_c ≤ 1`. Пример: если верны 80% проверенных предсказаний класса, то при `N_c=100` получим `W_c≈0,9998`, при `N_c=10 000` — `≈0,9810`, при `N_c=100 000` — `≈0,8736`. Так задумано, чтобы малая статистика почти не влияла. Для объёма одного дома `τ=100000` может оказаться настолько большим, что поправка практически не сработает; менять его нужно по фактическому числу проверок и испытаниям на отложенных данных, а не по желаемому направлению результата.

**Что формула обнаруживает.** Большое число проверенных ошибочных *предложений* класса снижает `C_c/N_c`: это сигнал избытка ложных срабатываний. **Чего она не обнаруживает.** Если модель не предложила класс `c` для настоящей проблемы этого класса, такая ошибка не попадёт в `N_c`. Чтобы видеть пропуски, надо также проверять часть сообщений с другими классами и с ответом «нет проблемы»; по ним отдельно считать долю найденных настоящих случаев и число пропусков. Тогда администратору можно показывать два направления перекоса: лишние предложения и пропущенные случаи. При `θ=1` исходная формула сама по себе не умеет компенсировать пропуски повышением класса.

Если операторы обычно проверяют только спорные или срочные сообщения, их ответы **не представляют весь поток**. Показывать `W_c` рядом с `N_c` и долей просмотренных сообщений; для оценки качества выбирать также случайную обезличенную проверочную выборку. Считать показатели отдельно по версии модели и периоду: после дообучения старая доля ошибок может перестать описывать новую версию. Модельная доразметка в `C_c` и `N_c` не входит.

### Как применять между обучениями

**Первый этап — только наблюдение.** На экране старшего администратора показать по каждому классу `N_c`, `C_c`, долю верных, `W_c`, ложные срабатывания и, при наличии проверенных отклонённых сообщений, пропуски. По этим числам выбирать классы для дополнительной разметки и следующего обучения. Администратор настраивает `α`, `τ`, `θ` и видит предварительный расчёт до применения настроек. Это не меняет ответы текущей модели.

**Возможный второй этап — осторожная поправка.** После калибровки оценок и проверки на новом периоде можно испытать умножение оценки каждого проблемного класса на `W_c`, затем нормировку оценок и повторное решение о классе. Отдельный фильтр «есть ли проблема» и проверку экстренности нельзя незаметно менять той же формулой. Сравнивать нужно не только среднюю точность, но и пропуски, ложные заявки и качество по редким классам. Если поправка ухудшает хоть один критичный показатель, оставить её только как статистику. Для классов с малым `N_c` и при смене версии модели влияние должно оставаться ограниченным.

Это **план проверки**, а не обещание прироста. Приведённая формула не обучает модель, не исправляет ошибки разметки и не заменяет периодическое дообучение на накопленных обезличенных сообщениях.
